Instalar una dependencia ejecuta código. No el código que se importará después, sino el que se ejecuta durante la propia instalación, sin que nadie haya revisado el paquete. Ese código corre con el mismo acceso al sistema que tiene quien lanzó el comando.

Los dos gestores ejecutaban ese código sin pedir confirmación, y los dos han dejado de hacerlo. pnpm 10 fue el primero, en enero de 2025, y lo anunció como un cambio incompatible hecho para aumentar la seguridad<Cite n={1} />; la versión 11 convirtió el aviso en un error y añadió una segunda defensa. npm llegó al mismo sitio en julio de 2026 con la versión 12, que bloquea los scripts de instalación de las dependencias salvo que estén nombradas en un campo nuevo, `allowScripts`<Cite n={12} />.

La comparación útil, entonces, ya no es entre nombres de gestor. Es entre versiones: dos de las cuatro que siguen bloquean avisando y sin detener la instalación, una bloquea con error, y una ejecuta.

Lo que sigue compara npm 11.8.0 y npm 12.0.2 con pnpm 10.0.0 y pnpm 11.26.0 en cuatro comportamientos, midiendo qué hace cada uno sin configurar nada. El punto 7 reúne la configuración con la que una versión de npm anterior a la 12 alcanza lo mismo. Cada celda sale de ejecutar el comando, salvo el valor de `1440` de la última fila, que es el que declara la documentación de pnpm. Los proyectos de prueba caben en dos archivos escritos completos más abajo.

| Comportamiento | npm 11.8.0 | npm 12.0.2 | pnpm 10.0.0 | pnpm 11.26.0 |
|---|---|---|---|---|
| `postinstall` de una dependencia | se ejecuta | bloqueado, aviso, salida 0 | bloqueado, aviso, salida 0 | bloqueado, salida 1 |
| `require` de un paquete no declarado | resuelve | resuelve | `MODULE_NOT_FOUND` | `MODULE_NOT_FOUND` |
| Instalación en CI con el bloqueo desfasado | instala otra versión, salida 0 | instala otra versión, salida 0 | salida 1 | salida 1 |
| Espera antes de resolver una versión recién publicada | el ajuste no existe | ajuste presente, sin valor | ninguna | 1440 minutos |

La tabla mide valores por defecto y no capacidades. La primera fila cambia con la versión mayor del gestor y no con ningún archivo del proyecto, así que la pregunta operativa es qué versión ejecuta la máquina. Las otras tres se igualan escribiendo dos archivos, salvo la segunda, que depende de cómo cada gestor coloca los paquetes en el disco.

## 1. La instalación ejecuta código de terceros

Un paquete puede declarar un script que corre al instalarse, y basta un proyecto de dos archivos para verlo sin descargar nada de la red.

```json
// package.json
{
  "name": "prueba-instalacion",
  "version": "1.0.0",
  "private": true,
  "dependencies": { "evil-postinstall": "file:./evil-postinstall" }
}
```

```json
// evil-postinstall/package.json
{
  "name": "evil-postinstall",
  "version": "1.0.0",
  "scripts": { "postinstall": "node -e \"require('fs').writeFileSync('EJECUTADO.txt','')\"" }
}
```

El nombre `evil-postinstall` está inventado para este artículo y no existe en el registro público, comprobado el 7 de septiembre de 2026 con `npm view evil-postinstall`, que devuelve `E404`.

Con npm 11.8.0 la instalación termina bien y el archivo aparece, sin que nada en la salida lo mencione.

```bash
npm install
# salida 0
ls evil-postinstall/EJECUTADO.txt
```

Con npm 12.0.2, el mismo comando sobre el mismo proyecto no crea el archivo. Avisa y termina en 0.

```bash
npm install
# npm warn install-scripts 1 package had install scripts blocked because they are
# npm warn install-scripts not covered by allowScripts:
# npm warn install-scripts   evil-postinstall@1.0.0 (postinstall: node -e "...")
# npm warn install-scripts Run `npm install-scripts ls` to review, or
# npm warn install-scripts `npm install-scripts approve <pkg>` to allow.
# salida 0
```

Que termine en 0 importa: un aviso no detiene la integración continua, así que el bloqueo protege la máquina pero no obliga a nadie a mirar la lista. Los dos comandos que menciona la salida son los que la revisan y la resuelven, y el permiso se concede desde `allowScripts` en `package.json`<Cite n={12} repeat />.

Con pnpm 11 la instalación se detiene antes de llegar ahí.

```bash
pnpm install
# [ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: evil-postinstall@file:evil-postinstall
# Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
# salida 1
```

De los cuatro comportamientos medidos, este es el único que termina con salida distinta de 0, y por eso es el único que detiene una tubería sin que nadie haya escrito nada.

Escribir un archivo vacío es inofensivo. El permiso que lo hace posible, en cambio, no distingue entre eso y leer variables de entorno, buscar credenciales en el disco o publicar paquetes con las credenciales de quien instala.

Ese último caso está documentado. En septiembre de 2025 el gusano Shai-Hulud se propagó por npm mediante un script de post-instalación, colocado en paquetes cuyos mantenedores habían sido comprometidos<Cite n={2} />, y CISA llegó a emitir una alerta<Cite n={3} />.

<Callout kind="nota" title="Bloquear los scripts no cubre todos los casos">
La carga maliciosa que afectó a `chalk`, `debug` y otros diecisiete paquetes el 8 de septiembre de 2025 no dependía de ningún script de instalación: estaba dentro del código del paquete y se activaba al ejecutarse en el navegador<Cite n={4} />. Un gestor que bloquea los scripts no habría cambiado nada en ese caso. Cierra una vía de entrada, no la categoría entera.
</Callout>

Bloquear por defecto responde a un problema que no se resuelve reconociendo. Cuando el paquete hostil es uno que nadie ha visto todavía, no hay nada que reconocer, y lo único que queda es restringir lo que cualquier paquete puede hacer mientras se instala.

En una versión de npm anterior a la 12, el mismo bloqueo se consigue con una línea en el archivo de configuración del proyecto. El ajuste `ignore-scripts` existe desde hace años y viene en `false`<Cite n={5} />. Sigue viniendo en `false` en npm 12: el bloqueo por `allowScripts` es un mecanismo nuevo y paralelo, no un cambio del valor de ese ajuste.

```ini
# .npmrc
ignore-scripts=true
```

Con ese archivo presente, la instalación anterior termina sin crear `EJECUTADO.txt`.

El bloqueo tiene un coste concreto. Paquetes como `esbuild`, `puppeteer` o `sqlite3` descargan o compilan su binario en ese mismo momento y sin eso no funcionan. Recuperarlos es cuestión de nombrarlos uno por uno, levantando el bloqueo solo para ese comando.

```bash
npm rebuild esbuild --ignore-scripts=false
```

La opción es obligatoria, porque con `ignore-scripts=true` en la configuración un `npm rebuild` a secas tampoco ejecuta nada.

## 2. Qué introdujo pnpm 10 y qué cambió en la 11

El cambio de pnpm 10, publicado el 7 de enero de 2025, fue dejar de ejecutar los scripts de las dependencias durante la instalación<Cite n={1} repeat />. La versión 10 avisa y continúa, y esa diferencia importa, porque un aviso con salida 0 no detiene la integración continua.

```
The following dependencies have build scripts that were ignored: esbuild
```

En esa versión el permiso se concede desde `package.json`, en el campo `pnpm.onlyBuiltDependencies`.

pnpm 11.0.0, del 28 de abril de 2026, cambió las dos cosas<Cite n={6} />. El aviso pasó a ser el error `ERR_PNPM_IGNORED_BUILDS` con salida 1, así que la instalación falla hasta que alguien decide. Y el permiso cambió de sitio: `onlyBuiltDependencies`, junto con `onlyBuiltDependenciesFile`, `neverBuiltDependencies`, `ignoredBuiltDependencies` e `ignoreDepScripts`, desapareció en favor de `allowBuilds` en `pnpm-workspace.yaml`<Cite n={7} />.

```yaml
# pnpm-workspace.yaml
allowBuilds:
  esbuild: true
```

Con esa entrada la instalación vuelve a terminar en 0 y el script de `esbuild` corre.

Hay además un efecto secundario que conviene conocer. Cuando pnpm 11 bloquea algo, escribe él mismo en `pnpm-workspace.yaml` y deja la entrada a medias:

```yaml
allowBuilds:
  esbuild: set this to true or false
```

Que un archivo versionado cambie durante un `pnpm install` no es lo habitual. El resultado, sin embargo, es que la decisión queda en el historial del repositorio en lugar de vivir en la máquina de quien instaló. El comando `pnpm approve-builds` recorre la lista de forma interactiva y escribe las respuestas en ese mismo sitio<Cite n={7} repeat />.

<Callout kind="riesgo" title="dangerouslyAllowAllBuilds anula la defensa completa">
El ajuste `dangerouslyAllowAllBuilds` desactiva la comprobación entera: la instalación termina en 0 sin nombrar nada, y aplica también a las dependencias que entren después<Cite n={7} repeat />. No es una excepción puntual sino la desactivación permanente del bloqueo. Un `allowBuilds` con tres nombres se revisa entrada por entrada; este ajuste no deja ninguna entrada que revisar.
</Callout>

## 3. El código importa paquetes que nadie declaró

Los scripts son el riesgo visible. El siguiente no necesita código hostil y no produce ningún error.

Un proyecto que solo declara `debug` recibe también `ms`, porque `debug` la necesita para funcionar. La pregunta es si el código del propio proyecto puede importarla.

```json
{
  "name": "fantasma",
  "version": "1.0.0",
  "private": true,
  "dependencies": { "debug": "4.3.4" }
}
```

```bash
node -e "require('ms')"
```

Con npm la línea funciona en las dos versiones de la tabla. Con pnpm falla con `MODULE_NOT_FOUND` en las dos suyas, porque pnpm no deja las dependencias indirectas al alcance de la raíz del proyecto.

Que un `require` funcione sin estar declarado significa que la versión de ese paquete la está eligiendo otro. Nadie la fijó, nadie la revisa cuando se actualiza, y desaparece el día que `debug` cambie su propia dependencia o la sustituya. Lo que termina ejecutándose es lo que resolvió el árbol de un tercero, que es una decisión que nadie tomó.

La comprobación es directa: instalar el proyecto con pnpm y arrancar la aplicación. Cada `MODULE_NOT_FOUND` que aparezca es un paquete que faltaba por declarar.

## 4. El archivo de bloqueo solo obliga si se le pide

Un archivo de bloqueo fija la versión exacta de cada dependencia, y deja de servir en cuanto el comando que corre en el servidor tiene permiso para reescribirlo.

La prueba parte de un proyecto instalado con `debug` en `4.3.4`. Después se cambia `package.json` a `4.4.0` sin tocar el bloqueo, que es exactamente lo que produce una rama mal fusionada.

```bash
CI=true npm install
# salida 0
node -p "require('./node_modules/debug/package.json').version"
# 4.4.0
```

npm instala una versión que el archivo de bloqueo no nombra, actualiza el archivo para que coincida y termina en 0, así que nada en la salida indica que se haya desviado. El mismo caso con pnpm:

```bash
CI=true pnpm install
# ERR_PNPM_OUTDATED_LOCKFILE
# salida 1
```

pnpm se detiene y deja `4.3.4` en su sitio, y la razón está documentada: `--frozen-lockfile` viene en `true` cuando detecta un entorno de integración continua, y en `false` fuera de él<Cite n={8} />.

npm tiene el equivalente exacto, con la diferencia de que hay que escribirlo. `npm ci` sale con error si el bloqueo no coincide con `package.json`, borra `node_modules` antes de empezar y no escribe nunca en ninguno de los dos archivos<Cite n={9} />.

```bash
npm ci
# npm error code EUSAGE
# salida 1
```

La diferencia, entonces, no está en el formato del archivo ni en lo que cada gestor es capaz de hacer. Los dos cumplen cuando se les pide. Está en cuál de los dos comportamientos se aplica cuando el comando no se escribió de forma explícita.

## 5. La edad de una versión como defensa

pnpm 11 trajo un segundo cambio de valor por defecto, y es el único de los cuatro que sigue siendo una diferencia real. Una versión recién publicada no se resuelve hasta que tenga al menos un día: el ajuste se llama `minimumReleaseAge`, se mide en minutos, y pasó de `0` a `1440`<Cite n={10} />.

```yaml
# pnpm-workspace.yaml
minimumReleaseAge: 1440
```

El ajuste responde a la forma que tienen estos incidentes. Las versiones maliciosas de `chalk` y `debug` se publicaron en dos tandas separadas por minutos, y se descubrieron el mismo día<Cite n={4} repeat />. Una espera de veinticuatro horas cubre justo ese intervalo: el paquete comprometido ya está publicado y todavía nadie lo ha detectado.

Conviene saber cómo se comporta cuando alguien pide una versión concreta. Pedirla de forma exacta no exime de la espera: con `debug` fijado a `4.4.3` y un `minimumReleaseAge` alto, la instalación falla.

```text
Error: ERR_PNPM_NO_MATURE_MATCHING_VERSION
  × installing dependencies
  ╰─▶ 2 versions do not meet the minimumReleaseAge constraint:
        debug@4.4.3 was published at 2025-09-13T17:25:19.732Z, within the
      minimumReleaseAge cutoff
  help: Run the install interactively to approve these picks, add them to
        minimumReleaseAgeExclude in pnpm-workspace.yaml, or wait for the
        packages to mature.
# salida 1
```

Las excepciones se nombran a mano en `minimumReleaseAgeExclude`: pnpm dice que lo añadas tú y no escribe en el archivo, a diferencia de lo que sí hace con `allowBuilds`. El ajuste vecino, `minimumReleaseAgeStrict`, decide otra cosa: si pnpm falla la resolución o cae a una versión anterior que sí cumple la restricción<Cite n={10} repeat />.

npm 12 incorporó el ajuste equivalente, con dos diferencias. Se llama `min-release-age`, se mide en días y no en minutos, y viene sin valor, así que por defecto no espera nada. La compañera `min-release-age-exclude` acepta nombres y patrones `minimatch`<Cite n={5} repeat />.

```bash
npm config get min-release-age
# npm 11.8.0 -> undefined   (el ajuste no existe)
# npm 12.0.2 -> null        (existe, sin valor)
```

Sigue existiendo además `before`, que fija todas las resoluciones a una fecha concreta y también viene sin valor.

## 6. Dónde los dos hacen lo mismo

Conviene separar lo que cambia de lo que no, porque la lista de diferencias reales es más corta de lo que sugiere cualquier comparación de gestores.

Los dos guardan la integridad de cada paquete en el archivo de bloqueo y los dos se niegan a continuar si el contenido descargado no coincide. Alterando a mano una entrada del bloqueo, npm falla con `EINTEGRITY` y pnpm con `ERR_PNPM_TARBALL_INTEGRITY`. Los dos tienen, como ya se vio, un comando que obliga a respetar ese archivo. Y ninguno de los dos inspecciona lo que hace el código del paquete una vez instalado, que es precisamente el caso de `chalk` y `debug`.

En sus versiones actuales los dos bloquean también los scripts de instalación, y lo hacen con la misma forma: una lista de nombres autorizados que se versiona con el repositorio y un comando interactivo que la rellena. Cambian el archivo y el vocabulario —`allowScripts` en `package.json` con `npm install-scripts approve`, `allowBuilds` en `pnpm-workspace.yaml` con `pnpm approve-builds`— y cambia la severidad, que es la diferencia que queda: npm 12 avisa y sale 0, pnpm 11 sale 1.

El registro también está cambiando por su cuenta. En septiembre de 2025 npm anunció la publicación mediante identidad verificada, que llama *trusted publishing*. Con ella llegaron la retirada de los tokens clásicos y un límite de siete días para la vida de los tokens granulares, con una caducidad más corta para los que tienen permiso de publicación<Cite n={11} />. Son cambios sobre cómo se publica un paquete y no sobre qué ocurre al instalarlo, así que se suman a lo anterior en lugar de sustituirlo.

## 7. Cómo configurar npm de forma segura

Nada de lo anterior obliga a cambiar de herramienta. Tres de los cuatro comportamientos se igualan en npm con dos archivos y un comando, y vale la pena tenerlos juntos en un solo sitio.

El paso previo, desde julio de 2026, es la propia versión. Subir a npm 12 trae el bloqueo de scripts y el ajuste de edad sin escribir nada, y no hay ninguna línea de configuración que consiga lo primero en una versión anterior con la misma cobertura. Lo que sigue vale para las dos situaciones: en npm 12 se acumula al bloqueo por `allowScripts`, y en una versión anterior es la única vía.

El primero es el archivo de configuración del proyecto, que se versiona con el repositorio para que valga para todo el equipo y no solo para quien lo escribió.

```ini
# .npmrc
ignore-scripts=true
```

El segundo es el comando de instalación en el servidor. `npm ci` respeta ese archivo, de modo que las dos defensas se acumulan en la misma línea.

```bash
npm ci
```

Con esas dos cosas, el proyecto del punto 1 se instala sin crear `EJECUTADO.txt` y termina en 0, que es el resultado de pnpm 10 y de npm 12 alcanzado por otro camino. Comprobar que el ajuste está activo en la máquina donde importa es una línea más:

```bash
npm config get ignore-scripts
# true
```

El tercero es la verificación de firmas del registro, que en un proyecto con dependencias reales confirma que lo descargado viene firmado por npm.

```bash
npm audit signatures
# 2 packages have verified registry signatures
```

La espera antes de resolver ya no es una diferencia de capacidad sino de valor por defecto, y se cierra nombrándola:

```ini
# .npmrc, npm 12 o posterior
min-release-age=1
```

Queda una diferencia que ningún ajuste de npm cubre. Las dependencias indirectas siguen siendo importables sin declararlas, porque el árbol plano forma parte de cómo npm resuelve, y eso se detecta con una herramienta de análisis y no con una línea de configuración.

## 8. Lo que cuesta cambiar de gestor

Si la decisión es migrar, hay consecuencias que aparecen el primer día.

El código que importaba paquetes no declarados deja de arrancar. Es el mismo `MODULE_NOT_FOUND` del punto 3, y el arreglo es declarar cada paquete, nunca desactivar el aislamiento para que el error se vaya.

La primera instalación se detiene con la lista de paquetes bloqueados y alguien tiene que revisarla. Esa revisión es el momento útil de la defensa, porque es cuando alguien lee por qué un paquete necesita ejecutar código durante la instalación.

`pnpm-workspace.yaml` pasa a ser parte del repositorio y cambia solo durante las instalaciones. Una entrada nueva que aparezca sin que nadie haya añadido una dependencia obliga a comprobar de dónde salió.

La espera de un día retrasa cualquier actualización recién publicada, incluida la corrección urgente que se estaba esperando.

## Lo que decide la protección

Ninguno de los cuatro comportamientos depende del nombre del gestor. Dependen de la versión instalada y de lo que haya escrito en los archivos de configuración, y las dos se comprueban con un par de comandos.

Un proyecto con pnpm 9 no bloquea nada, y uno con npm 11 tampoco. Uno con pnpm 10 o con npm 12 avisa y sigue adelante. Uno con npm 11 y un `.npmrc` con `ignore-scripts=true` bloquea más que npm 12 sin configurar, porque no depende de una lista de excepciones. La primera comprobación es determinar cuál de esos casos aplica, y son dos líneas:

```bash
npm --version
pnpm --version
```

Declarar la versión en `package.json` documenta la intención, pero por sí solo no la impone:

```json
{ "packageManager": "pnpm@10.11.0" }
```

En un proyecto con ese campo y sin Corepack activado, `pnpm --version` sigue respondiendo la versión que hay instalada en la máquina, que puede ser una anterior a todo lo descrito aquí. Fijar la versión de verdad exige habilitar Corepack o instalarla en el propio proyecto, y hasta que eso ocurra el campo es una declaración y no un control. La protección no depende de lo que el proyecto declare usar, sino de lo que la máquina ejecuta.
