Un agente de programación es un modelo de lenguaje con herramientas para leer archivos, editarlos y ejecutar órdenes. Alrededor hay un programa que ejecuta esas herramientas y le devuelve el resultado. Esa es la diferencia con un chat: el chat responde con texto que alguien tiene que aplicar, y el agente aplica el cambio en el repositorio.

El cambio en el trabajo de quien programa es de reparto, no de cantidad. Escribir cada línea deja de ser la tarea principal, y pasan a serlo tres: decidir qué hay que construir, dar al agente una forma de comprobar si lo consiguió, y revisar lo que dejó escrito.

Esta guía asume que quien la lee sabe programar y apenas empieza a usar IA para hacerlo. Cada sección explica un concepto con un ejemplo real, qué hace cada parte de ese ejemplo, y los pasos para aplicarlo en un proyecto propio. Al final hay un prompt que se copia con un botón y deja configurado el entorno entero: instrucciones del proyecto, permisos, skills, cuatro revisores y seis agentes de trabajo. El mismo prompt propone herramientas y colecciones de skills opcionales.

Los ejemplos usan Claude Code en la terminal. Se instala con el instalador nativo que publica su documentación. A partir de ahí se abre entrando en el directorio del proyecto y ejecutando `claude`, que pide iniciar sesión la primera vez<Cite n={1} />. La misma herramienta existe como extensión de VS Code y de JetBrains, como aplicación de escritorio y en el navegador, y todas comparten el mismo motor y la misma configuración<Cite n={1} repeat />. En Cursor el agente viene dentro del editor y no hay nada que instalar aparte.

Versiones medidas: Claude Code 2.1.283, git 2.49.0, Node.js 24.19.0 y npm 11.8.0, el 26 de septiembre de 2026. La documentación de Cursor se consultó el 8 de septiembre de 2026. Todo el código está reconstruido para el artículo.

## 1. Qué hace un agente que un chat no hace

Hay tres formas de usar un modelo de lenguaje para programar, y se diferencian en quién aplica el cambio.

El **autocompletado** propone el final de la línea que se está escribiendo, dentro del editor. Quien programa acepta o rechaza cada sugerencia, así que el control es total y el alcance llega a una función como máximo.

El **chat** recibe una pregunta y devuelve texto. El código que produce hay que copiarlo al proyecto a mano, adaptarlo a los nombres reales y comprobar que compila. El modelo no ha visto el repositorio, así que inventa la estructura que le parece razonable.

El **agente** recibe una tarea, decide qué archivos leer, los lee, escribe los cambios y ejecuta órdenes para comprobarlos. La documentación de Claude Code define ese trabajo como aquel en el que la IA lee archivos, ejecuta órdenes y hace cambios de forma autónoma, mientras alguien observa, corrige o se aparta. Lo contrapone a los asistentes de chat, que solo responden con texto que hay que aplicar a mano<Cite n={2} />.

Lo que convierte un modelo en agente son las herramientas. Una **herramienta** es una acción que el modelo puede pedir: leer un archivo, editarlo, ejecutar una orden en la terminal, buscar en el proyecto. La misma documentación lo dice sin rodeos: sin herramientas, el modelo solo puede responder con texto<Cite n={2} repeat />.

Las tres formas conviven en la misma jornada. El autocompletado sigue siendo lo más rápido para terminar una línea. El chat sirve para preguntar algo que no toca el repositorio, y el agente para las tareas que cruzan varios archivos.

**Cómo se comprueba.** En una sesión de agente aparecen las llamadas a herramientas antes de la respuesta: qué archivo leyó, qué orden ejecutó y qué devolvió. En Claude Code el detalle completo se abre con `Ctrl+O`, que alterna el visor de transcripción<Cite n={3} />. Si en toda la sesión solo hubo texto, no actuó como agente.

## 2. El bucle es la definición completa

Un agente no responde una sola vez. Repite un ciclo hasta que considera terminada la tarea, y la documentación lo describe en cuatro pasos: reunir contexto, actuar, verificar el resultado y repetir. Cada uso de una herramienta devuelve información que decide el paso siguiente<Cite n={2} repeat />.

Un ejemplo sobre una tarea sencilla. El agente busca el archivo que hay que tocar, lo lee, escribe el cambio, ejecuta las pruebas, lee el fallo que devuelven, corrige y vuelve a ejecutarlas. Son seis llamadas a herramientas para algo que en un chat habría sido una respuesta.

Quien ejecuta esas herramientas no es el modelo. El modelo solo produce texto, incluida la petición de usar una herramienta. Alrededor hay un programa que interpreta esa petición, la ejecuta contra el sistema de archivos o la terminal y le devuelve la salida. Ese programa se llama *harness*, y la documentación lo define como las herramientas, la gestión de contexto y el entorno de ejecución que convierten un modelo en un agente<Cite n={2} repeat />.

Cursor describe su agente con las mismas tres piezas: las instrucciones que guían su comportamiento, las herramientas de edición, búsqueda y ejecución, y el modelo elegido para la tarea<Cite n={4} />. Por eso elegir modelo y elegir herramienta son dos decisiones distintas.

**Cómo se comprueba.** Se ejecuta una tarea y se cuentan las llamadas a herramientas anteriores a la respuesta final. Un agente que resolvió algo sin leer ningún archivo lo escribió de memoria.

## 3. La ventana de contexto y la orden `/context`

La **ventana de contexto** es la memoria de trabajo de la sesión: el historial de la conversación, los archivos leídos, la salida de las órdenes, el archivo de instrucciones del proyecto y las instrucciones del sistema<Cite n={2} repeat />. El agente no sabe nada que no esté ahí dentro. Se mide en **tokens**, la unidad en la que el modelo cuenta el texto, que para Claude equivale a unos 3,5 caracteres en inglés<Cite n={5} />.

`/context` enseña cómo está repartida. Esta es su salida, recortada, al abrir una sesión nueva en un repositorio con un archivo de instrucciones del proyecto de 29 tokens y uno personal de 96:

```text
**Tokens:** 19k / 1m (2%)

| Category                | Tokens | Percentage |
|-------------------------|--------|------------|
| System prompt           | 2.3k   | 0.2%       |
| System tools            | 4.6k   | 0.5%       |
| MCP server instructions | 686    | 0.1%       |
| Custom agents           | 374    | 0.0%       |
| Memory files            | 125    | 0.0%       |
| Skills                  | 9.9k   | 1.0%       |
| Messages                | 1k     | 0.1%       |
| Free space              | 948k   | 94.8%      |
| Autocompact buffer      | 33k    | 3.3%       |
```

Cada fila es una cosa que se paga en todas las peticiones de la sesión:

- **System prompt** y **System tools**: las instrucciones fijas de la herramienta y la descripción de sus herramientas. No dependen del proyecto.
- **MCP server instructions**: lo que añaden los servidores de herramientas externas conectados. Se explican en el punto 11.
- **Custom agents** y **Skills**: la descripción de cada subagente y de cada skill instalada, no su contenido completo.
- **Memory files**: los archivos de instrucciones del proyecto y del usuario, del punto 8.
- **Messages**: la conversación. Es la fila que crece con cada archivo leído y cada orden ejecutada.
- **Autocompact buffer**: el espacio reservado para resumir la conversación cuando la ventana se llena.

Ese resumen automático se llama **compactación**. Descarta primero las salidas de herramientas antiguas y después resume el resto; el archivo de instrucciones se vuelve a leer del disco, y lo que solo se dijo en la conversación se puede perder<Cite n={2} repeat />. Como la conversación entera viaja en cada petición, una sesión larga también cuesta más<Cite n={6} />.

**Cómo se hace.**

1. Se ejecuta `/context` al abrir la sesión y se anota el total.
2. Terminada una tarea, `/clear` empieza una conversación nueva con el contexto vacío antes de la siguiente.
3. Si una tarea larga se acerca al límite, `/compact` resume la conversación en ese momento, y admite una instrucción: `/compact conserva la lista de archivos tocados`.
4. Lo que tenga que sobrevivir a la compactación se escribe en el archivo de instrucciones, no en un mensaje.

**Cómo se comprueba.** Se ejecuta `/context` antes y después de la primera tarea. La diferencia en **Messages** es lo que costó esa tarea, y es el dato que dice cuándo conviene cerrar la sesión.

## 4. Qué tareas le van bien a un agente

Una tarea encaja en un agente cuando existe una orden que decide si está terminada. La documentación llama a eso **bucle de verificación**: se le entrega una comprobación que pueda ejecutar, una prueba, una compilación o una comparación, y el agente itera hasta que pasa. Sin ella, lo único que decide que terminó es el propio agente<Cite n={2} repeat />.

| Le va bien | Orden que decide el final |
|---|---|
| Corregir un fallo que se reproduce con una prueba | la prueba pasa |
| Migrar una llamada a una biblioteca en veinte archivos | el proyecto compila |
| Escribir pruebas para código que no las tiene | las pruebas pasan y fallan al romper el código |
| Resolver los avisos de un linter | el linter termina sin avisos |

Le van mal las tareas sin esa orden: decidir la arquitectura de un módulo nuevo, ajustar el diseño visual sin una imagen de referencia, o cualquier cosa cuyo criterio sea que a alguien le parezca bien. Ahí el agente sirve para explorar alternativas, y la decisión sigue siendo de quien programa.

<Callout kind="nota" title="Una tarea sin comprobación se puede partir en dos que sí la tienen">
	«Mejorar el rendimiento de la pantalla de pedidos» no tiene criterio. «Escribir una medición que imprima el tiempo de la consulta actual» sí lo tiene. «Bajar ese tiempo por debajo de 200 ms sin cambiar el resultado», también, y el agente puede ejecutar las dos.
</Callout>

La condición se puede declarar con `/goal`. Al terminar cada turno, un modelo pequeño comprueba si se cumple, y mientras no se cumpla el agente empieza otro turno en lugar de devolver el control<Cite n={7} />.

```text
/goal todas las pruebas de test/auth pasan y el linter termina sin avisos, o parar tras 20 turnos
```

Cada parte de esa línea tiene un trabajo. «Todas las pruebas de test/auth pasan» es el estado final medible. «El linter termina sin avisos» es una restricción que no se puede romper por el camino. «O parar tras 20 turnos» acota cuánto dura. El evaluador no ejecuta nada por su cuenta: juzga lo que el agente haya dejado escrito en la conversación, así que la condición tiene que poder demostrarse con la salida de una orden<Cite n={7} repeat />. `/goal clear` la retira antes de tiempo.

**Cómo se comprueba.** Antes de escribir la petición se nombra la orden que va a decidir si está terminada. Si no aparece ninguna, la tarea todavía no está lista para un agente.

## 5. Cómo se escribe la primera petición

El agente resuelve el enunciado que recibe, así que el enunciado tiene que traer la condición que se va a comprobar después. «Añade la cancelación de pedidos» no la trae. Esta petición sí:

```text
En src/pedidos.js, añade cancelarPedido(pedidos, id).
Devuelve null si el pedido no existe.
Si existe, cambia estado a 'cancelado' y devuelve el pedido.
No añadas dependencias.
Criterio: node --test pasa con las dos pruebas de tests/pedidos.test.js.
```

Qué hace cada línea:

- **El archivo** acota dónde se escribe y evita que el agente lea medio repositorio buscándolo.
- **El comportamiento en cada caso** da algo contra lo que contrastar el resultado, incluido el caso de error.
- **La restricción** cierra por adelantado una decisión que, sin decir nada, el agente toma solo.
- **El criterio** nombra la orden que decide el final y el resultado que tiene que devolver.

A eso se añade lo que el modelo no puede deducir del código, como la versión del gestor de paquetes. En la primera sesión va en la petición; el punto 8 explica dónde se guarda para no repetirla.

En **modo plan** el agente lee, busca y ejecuta órdenes de exploración, pero no edita el código: presenta un plan y espera aprobación<Cite n={2} repeat />. La primera revisión ocurre sobre un texto corto, y un enfoque equivocado se corrige sin revertir archivos.

**Cómo se hace.**

1. Se escribe `/plan` seguido de la petición, o se pulsa `Shift+Tab` hasta que la barra de estado indique `plan mode on`<Cite n={8} />.
2. Se lee el plan. Si nombra archivos que la petición no pedía tocar, se responde corrigiéndolo.
3. Con el plan aprobado, el agente sale del modo plan y aplica los cambios.

**Cómo se comprueba.** La petición contiene una orden ejecutable y el resultado que esa orden tiene que devolver. Si no lo contiene, decidir si el cambio está terminado obliga a leerlo entero.

## 6. Cómo se detiene, se redirige y se deshace

Un agente trabaja durante varios turnos, así que hace falta pararlo a mitad y volver atrás. Hay tres mecanismos y cubren cosas distintas.

| Mecanismo | Qué hace | Cuándo se usa |
|---|---|---|
| `Esc` | Detiene la respuesta o la herramienta en curso y conserva lo hecho hasta ahí | el agente va por mal camino y basta con corregir el rumbo |
| `/rewind` o `Esc` `Esc` | Abre el menú de puntos de restauración | una tanda de ediciones sobra entera |
| git | Devuelve el repositorio a un commit | todo lo que los dos anteriores no cubren |

`Ctrl+C` también interrumpe; con nada en ejecución, la primera pulsación limpia la entrada y la segunda cierra el programa<Cite n={3} repeat />.

Claude Code captura el estado del código antes de cada petición, y a cada captura la llama punto de restauración. Guarda las de los cien más recientes de la sesión<Cite n={9} />. `/rewind` lista las peticiones enviadas, y sobre la elegida ofrece hasta cuatro acciones; las dos que restauran código solo aparecen si hubo ediciones después de ese punto<Cite n={9} repeat />:

- **Restore code and conversation**: devuelve el código y la conversación a ese punto.
- **Restore conversation**: vuelve a ese mensaje y deja el código como está.
- **Restore code**: deshace los cambios de archivos y conserva la conversación.
- **Summarize from here**: resume la conversación desde ese punto para liberar contexto.

<Callout kind="riesgo" title="Un punto de restauración no cubre lo que hizo la terminal">
	El seguimiento solo alcanza a las ediciones hechas con las herramientas de archivo del agente. Los archivos que modifique una orden de terminal, como `rm`, `mv` o `cp`, no se pueden deshacer desde el menú. Tampoco se restauran, en general, las ediciones de un subagente ni los cambios hechos fuera de la sesión. La documentación lo enuncia: los puntos de restauración sirven dentro de una sesión y no sustituyen al control de versiones<Cite n={9} repeat />.
</Callout>

**Cómo se hace.**

1. Antes de la petición, `git status --porcelain` tiene que salir vacío; si no, se confirma o se guarda lo pendiente.
2. Si el agente se desvía, `Esc` y una frase que lo corrija.
3. Si el resultado sobra entero, `/rewind`, se elige la petición y **Restore code**.
4. Después se ejecuta otra vez `git status --porcelain`.

**Cómo se comprueba.** Si en el último paso quedan archivos modificados, son los que el menú no cubre, y se descartan con git.

## 7. Cómo se usa el agente para aprender y no solo para producir

Un agente que escribe el código deja fuera la parte del trabajo donde se aprende. Hay tres formas de pedir lo mismo que la conservan, y las tres son peticiones normales:

| En lugar de | Se pide | Qué se obtiene |
|---|---|---|
| «Arregla el fallo de validación» | «En modo plan, explica qué archivos intervienen y por qué falla» | la explicación sobre el código real, sin cambios |
| «Añade validación al endpoint» | «Dónde se valida el cuerpo de la petición y en qué archivo empieza el camino» | un mapa que sirve para las tareas siguientes |
| «Escribe la función» | «Revisa esta versión mía contra manejo de errores, casos límite y nombres» | la diferencia entre las dos versiones |

Preguntar dónde está algo es lo que un agente responde mejor, porque puede buscarlo en vez de suponerlo. Lo que afirma sobre una biblioteca o un estándar se contrasta con su documentación, porque lo dice con la misma seguridad cuando lo sabe y cuando lo supone.

**Cómo se comprueba.** Después de una explicación se cierra la sesión y se reconstruye lo explicado sin ella. Lo que no se pueda reconstruir es lo que hay que volver a leer.

## 8. El archivo de instrucciones: `AGENTS.md` y `CLAUDE.md`

Cada sesión empieza con la ventana de contexto vacía. El **archivo de instrucciones** resuelve eso: se escribe una vez y la herramienta lo carga al principio de cada sesión.

`AGENTS.md` es el nombre que leen varias herramientas. Claude Code lo lee directamente desde la versión 2.1.277, siempre que el repositorio no tenga un `CLAUDE.md`; si lo tiene, lee solo `CLAUDE.md`, que puede importar `AGENTS.md` con una línea `@AGENTS.md`<Cite n={10} />. Hay además una versión personal en `~/.claude/CLAUDE.md` para las preferencias de todos los proyectos, y todos los archivos encontrados se suman en el contexto<Cite n={10} repeat />.

Un archivo completo para un proyecto pequeño:

```markdown
# pedidos

## Órdenes
- Instalar: npm ci
- Pruebas: node --test
- Una sola prueba: node --test tests/pedidos.test.js
- Linter: npx eslint .

## Entorno
- Node.js 24, npm 11. Módulos ES.

## Convenciones
- Las fechas se guardan en UTC y se formatean solo en la interfaz.
- Las funciones de src/ no escriben en consola; devuelven el error.

## Antes de dar una tarea por terminada
1. node --test termina en 0.
2. npx eslint . termina sin avisos.
3. No se añadió ninguna dependencia que la tarea no pidiera.
```

Qué hace cada bloque:

- **Órdenes**: el agente no tiene que adivinar cómo se prueba ni con qué gestor se instala. La de una sola prueba le ahorra ejecutar la suite entera en cada iteración.
- **Entorno**: lo que no se deduce con certeza leyendo el código.
- **Convenciones**: decisiones del proyecto que el código no explica.
- **Antes de dar una tarea por terminada**: el bucle de verificación del punto 4, escrito una vez para todas las tareas.

Lo que no entra es lo que el agente puede leer del disco: el listado de directorios o la lista de dependencias. La documentación recomienda menos de 200 líneas, porque un archivo más largo consume contexto y baja la adherencia, e instrucciones verificables: «usa indentación de 2 espacios» en lugar de «formatea bien el código»<Cite n={10} repeat />.

Estas instrucciones son contexto y no configuración obligatoria. Lo que tenga que ocurrir siempre en un momento fijo, como formatear después de cada edición, se configura como *hook*: una orden que la herramienta ejecuta en ese punto del ciclo sin consultar al modelo<Cite n={10} repeat />.

**Cómo se hace.**

1. `/init` analiza el proyecto y genera un primer `CLAUDE.md`. Si el proyecto ya usa `AGENTS.md`, se escribe ahí en su lugar.
2. Se ejecuta cada orden que el archivo nombra y se borra la que no funcione.
3. Se añaden las convenciones y la lista de «antes de dar una tarea por terminada».
4. `/memory` abre los archivos de instrucciones para editarlos más adelante.

**Cómo se comprueba.** `/context all` lista los archivos cargados bajo **Memory Files**, con su ruta y sus tokens. Si el archivo no aparece ahí, el agente no lo está leyendo.

## 9. Lo que no hace falta siempre se guarda como skill

El archivo de instrucciones se carga entero en cada sesión, así que todo lo que se le añade se paga en todas las tareas. Para lo que solo hace falta a veces hay dos mecanismos que cargan bajo condición.

Las **reglas por ruta** son archivos en `.claude/rules/` con una cabecera `paths`, y solo entran en contexto cuando el agente trabaja con un archivo que coincide<Cite n={10} repeat />:

```markdown
---
paths:
  - "src/api/**/*.ts"
---

- Todo endpoint valida la entrada antes de usarla.
- Los errores usan el formato de respuesta estándar.
```

Una **skill** es una carpeta con un archivo `SKILL.md` que contiene instrucciones, conocimiento o un procedimiento. Al abrir la sesión solo se carga su descripción; el contenido completo entra cuando la petición encaja con esa descripción o cuando se invoca con `/nombre`<Cite n={11} />.

```markdown
---
name: resumen-de-cambios
description: Resume los cambios sin confirmar y señala lo que tenga riesgo. Úsala cuando se pregunte qué cambió o se pida un mensaje de commit.
disable-model-invocation: false
---

Cambios actuales:

!`git diff HEAD --stat`

Resume esos cambios en dos o tres puntos y después enumera los riesgos:
manejo de errores ausente, valores fijos en el código o pruebas por actualizar.
Si no hay cambios, dilo.
```

Qué hace cada pieza:

- **`name`**: el nombre de la orden, `/resumen-de-cambios`. Minúsculas, números y guiones, igual que la carpeta<Cite n={12} />.
- **`description`**: el único texto con el que el agente decide si la carga sola. Dice qué hace y cuándo se usa, con las palabras que alguien escribiría al pedirlo.
- **`disable-model-invocation`**: con `true`, la skill solo se ejecuta cuando alguien escribe su orden, nunca por decisión del agente<Cite n={11} repeat />.
- **`` !`orden` ``**: se ejecuta antes de enviar la skill al modelo, y su salida sustituye a la línea<Cite n={11} repeat />.
- **El cuerpo**: las instrucciones, que entran en la conversación como un solo mensaje.

Otra variable útil es `$ARGUMENTS`, que se sustituye por lo que se escriba detrás de la orden: con `/arreglar-issue 123`, el cuerpo recibe `123`<Cite n={11} repeat />.

El formato no es de una sola herramienta. Las skills siguen el estándar abierto Agent Skills, que fija `name` y `description` como obligatorios y `license`, `compatibility`, `metadata` y `allowed-tools` como opcionales<Cite n={12} repeat />. `disable-model-invocation` es una extensión de Claude Code.

**Cómo se hace.**

1. Se crea `.claude/skills/resumen-de-cambios/SKILL.md` para este proyecto, o en `~/.claude/skills/` para todos los de la máquina<Cite n={11} repeat />.
2. Se pega el ejemplo y se ajusta la descripción a cómo se pediría en el equipo.
3. Se abre una sesión nueva, porque las descripciones se leen al empezar.

**Cómo se comprueba.** Se escribe `/` en la sesión y la skill tiene que aparecer en la lista. Después se hace una petición que encaje con su descripción, sin nombrarla, y se comprueba si se cargó sola. Si no se carga, el problema está en la descripción.

## 10. Subagentes: revisores con su propio contexto

Un **subagente** es un asistente especializado que corre en su propia ventana de contexto, con sus propias instrucciones y herramientas. No ve la conversación principal, y al terminar solo devuelve su resumen<Cite n={13} />. Eso lo hace útil para revisar: quien revisa no arrastra el razonamiento de quien escribió el cambio.

Se define en un archivo Markdown en `.claude/agents/` para el proyecto o en `~/.claude/agents/` para todos<Cite n={13} repeat />:

```markdown
---
name: revisor-calidad
description: Revisa si un cambio se va a poder mantener. Úsalo sobre el diff antes de confirmar.
tools: Read, Grep, Glob, Bash
model: sonnet
---

Tu pregunta es una: ¿este cambio se va a poder sostener?
Busca funciones que el proyecto ya tiene y el cambio reimplementa,
imports sin usar o que cruzan una capa, y funciones que
hacen varias cosas a la vez.
Cada hallazgo lleva archivo:línea, el fallo concreto y qué ejecutaste para comprobarlo.
Cero hallazgos es un resultado válido.
```

Qué hace cada campo:

- **`name`** y **`description`**: obligatorios. La descripción decide cuándo el agente principal le delega el trabajo<Cite n={13} repeat />.
- **`tools`**: las herramientas permitidas. Un revisor no necesita editar, así que no recibe `Edit` ni `Write`.
- **`model`**: el modelo que usa; `inherit` toma el de la sesión.
- **El cuerpo**: sus instrucciones, que sustituyen a las de la herramienta.

Una revisión útil se reparte en cuatro subagentes con una pregunta cada uno. El de **seguridad** pregunta si el cambio deja a alguien hacer o ver algo que no debería. El de **calidad**, si deja el código mejor o peor: duplicación, imports, estructura. El de **errores y tipos** pregunta si algún error puede pasar sin que nadie se entere, o si los tipos permiten un estado que no debería existir. El de **pruebas** es la rutina: ejecuta la suite, los tipos y el linter, mide si las pruebas fallarían al romper el código, y ejecuta lo que el de seguridad necesita comprobar. Un solo revisor con las cuatro preguntas reparte la atención y devuelve una lista larga de avisos menores.

Lo que separa un revisor útil de uno que genera ruido es lo que exige a cada hallazgo, y varias fuentes públicas lo dejan escrito. La guía de auditoría de Cloudflare no acepta un hallazgo de seguridad sin nombrar quién cruza qué frontera de confianza y qué resultado concreto produce, y da gravedad solo a lo confirmado<Cite n={14} />. El revisor de seguridad de Anthropic solo reporta lo que tiene más de un 80 % de confianza y descarta de forma explícita categorías que suelen ser ruido<Cite n={15} />. ECC obliga a citar la línea exacta, a leer a quien llama al código y a aceptar que una revisión sin hallazgos es válida<Cite n={16} />. La guía de revisión de Google pide no aceptar cambios que empeoren la salud del código del sistema<Cite n={17} />.

Cada subagente consume tokens con su propio modelo, y el campo `model` decide cuál. Si ni la llamada ni la definición lo fijan, Claude Code usa el modelo de la variable `CLAUDE_CODE_SUBAGENT_MODEL` y, sin ella, el de la conversación principal<Cite n={13} repeat />. Ese suele ser el más caro. Un revisor que busca en archivos no necesita el mismo modelo que uno que razona sobre autorización, así que cada definición fija el suyo.

Varios subagentes que editan a la vez el mismo directorio se pisan. Los árboles de trabajo de git lo evitan: cada subagente trabaja en otro directorio con su propia rama, y el agente principal integra las ramas de una en una. En Claude Code se activa con `isolation: worktree` en la definición del subagente, y por omisión el árbol parte de la rama principal del remoto, no de la rama actual<Cite n={18} />.

Los agentes de trabajo se reparten igual que los revisores, cada uno con su nivel de modelo. `explorador` y `documentador` usan un modelo pequeño: el primero localiza y explica código, y el segundo pone al día la documentación. `arquitecto` usa un modelo mayor para diseñar y partir el trabajo en piezas. `implementador` resuelve una pieza en su propio árbol de trabajo, con un modelo intermedio. `resolutor-compilacion`, con el mismo nivel, devuelve la compilación, los tipos y el linter a verde con el cambio mínimo. `limpiador` completa el grupo: código muerto y duplicación, a petición, también con un modelo intermedio. Solo el agente principal los lanza, e integra sus ramas de una en una.

Un workflow lleva lo mismo a otra escala: un guion que lanza decenas de subagentes por fases. Claude Code avisa cuando uno programa más de 25 agentes, y admite una guía de tamaño que apunta a menos de 5, de 10 o de 50<Cite n={19} />.

**Cómo se hace.**

1. Se crea `.claude/agents/revisor-calidad.md` con el ejemplo.
2. Se lanza nombrándolo: `@agent-revisor-calidad revisa el diff actual`<Cite n={13} repeat />.
3. Los cuatro revisores, los seis agentes de trabajo y la skill `revisar-cambio` que lanza la revisión los crea el prompt del punto 14.

**Cómo se comprueba.** Se introducen a propósito dos fallos de calidad, una utilidad que ya existe reimplementada y un import sin usar, y se lanza el revisor. Si no los señala, sus instrucciones no bastan.

## 11. Los plugins instalan lo que otro ya escribió

Un **plugin** es un paquete instalable que agrupa skills, agentes, *hooks* y servidores MCP<Cite n={20} />. **MCP**, siglas de Model Context Protocol, es un protocolo abierto para conectar un modelo con fuentes de datos y herramientas externas<Cite n={5} repeat />. Un servidor MCP añade herramientas nuevas al agente, para Slack, Jira, una base de datos o un navegador.

Los plugins se distribuyen en catálogos llamados *marketplaces*. El catálogo oficial de Anthropic, `claude-plugins-official`, queda registrado la primera vez que se abre una sesión interactiva, así que instalar de él es una sola orden<Cite n={20} repeat />:

```shell
/plugin install commit-commands@claude-plugins-official
```

`commit-commands` es el nombre del plugin, que añade órdenes para confirmar, subir y abrir pull requests, y lo que va detrás de `@` es el catálogo del que sale. Un catálogo de terceros se registra antes con `/plugin marketplace add <usuario>/<repositorio>`, que no instala nada<Cite n={20} repeat />. `/plugin` sin argumentos abre el panel de catálogos, plugins instalados y errores de carga, y `/mcp` gestiona las conexiones con servidores MCP<Cite n={21} />.

Antes de instalar, la ficha de cada plugin enseña dos datos. **Context cost** es lo que añade a cada mensaje y lo que añaden sus skills y agentes al cargarse. **Will install** lista las órdenes, agentes, skills, *hooks* y servidores que trae<Cite n={20} repeat />. El primero se paga en todas las sesiones, también en las que no se usa el plugin.

Los plugins de inteligencia de código conectan un servidor de lenguaje, la tecnología que da al editor el salto a la definición. Con uno instalado, el agente ve los errores de tipos que introducen sus propias ediciones antes de compilar. El plugin no incluye el servidor, que se instala aparte<Cite n={22} />.

<Callout kind="riesgo" title="Un plugin ejecuta código con los permisos de quien lo instala">
	La documentación lo enuncia sin matices: un plugin instalado puede ejecutar código arbitrario en la máquina con los privilegios del usuario. Anthropic añade que no controla qué servidores, archivos u otro software incluye un plugin, ni puede verificar que funcione como dice<Cite n={23} />. Antes de instalar uno de un tercero se abre su repositorio y se lee qué trae.
</Callout>

**Cómo se comprueba.** Se ejecuta `/context` antes y después de instalar. Un plugin que añade contexto en cada turno y no se usa nunca se desinstala.

## 12. Qué permisos se le dan

Un agente ejecuta órdenes y lee archivos, así que hay dos decisiones antes de la primera sesión larga: qué se detiene a preguntar y qué archivos puede leer.

Lo primero lo fijan los **modos de permiso**, que se recorren con `Shift+Tab` y se ven en la barra de estado<Cite n={8} repeat />:

| Modo | Qué hace |
|---|---|
| `default` | Pregunta la primera vez que se usa cada herramienta. La barra lo muestra como `manual mode on`. |
| `acceptEdits` | Acepta sin preguntar las ediciones y las órdenes básicas de archivos dentro del proyecto. |
| `plan` | Lee y explora, pero no edita el código. |
| `auto` | Aprueba las herramientas con comprobaciones de seguridad en segundo plano. |
| `bypassPermissions` | Omite las peticiones de permiso. |

El último es el que se activa el primer día para dejar de responder preguntas. Su documentación restringe el uso a entornos aislados, contenedores o máquinas virtuales donde el agente no pueda causar daño<Cite n={24} />.

Lo segundo importa porque el agente envía al servidor del proveedor el contenido de los archivos que lee, y un `.env` con credenciales entra en ese envío igual que el código. La exclusión se declara en `.claude/settings.json`<Cite n={25} />:

```json
{
	"permissions": {
		"deny": ["Read(./.env)", "Read(./.env.*)"]
	}
}
```

`deny` es la lista de acciones que la herramienta rechaza siempre. `Read(./.env)` es la herramienta de lectura sobre ese archivo exacto, y `Read(./.env.*)` cubre `.env.local`, `.env.production` y los demás. Que el archivo esté en `.gitignore` no lo protege: medido sin la regla, la herramienta de lectura devolvió el archivo sin error. Con la regla, devuelve el bloqueo:

```text
File is in a directory that is denied by your permission settings.
```

La regla alcanza también a las órdenes de terminal que nombran el archivo, como `cat .env` o `head .env`. No alcanza a un guion que abra el archivo por su cuenta, como un programa de Node o de Python<Cite n={24} repeat />.

Cursor parte de otro punto. Ignora por defecto lo listado en `.gitignore` y una lista propia que incluye `.env*`, y lo demás se excluye en `.cursorignore`. La misma documentación indica que la terminal y las herramientas externas del agente no pueden bloquear el acceso a lo cubierto por ese archivo<Cite n={26} />.

En las dos herramientas la exclusión vive en la configuración y no en el archivo de instrucciones. Las reglas de permiso las aplica la herramienta y no el modelo<Cite n={24} repeat />, así que una línea en `AGENTS.md` que diga «no leas `.env`» no cambia lo que la herramienta permite.

Queda una decisión de coste: qué modelo usa la sesión. Se cambia con `/model`, y la documentación recomienda empezar con Sonnet, que resuelve bien la mayoría de las tareas de programación y cuesta menos que Opus<Cite n={6} repeat />.

**Cómo se comprueba.** Se pide al agente el contenido de `.env`. Con la regla puesta, la herramienta devuelve el bloqueo en lugar del archivo. Que el modelo conteste que no piensa hacerlo no comprueba nada, porque esa respuesta no la produce la regla.

## 13. Cómo se revisa lo que hizo

Un agente edita los archivos directamente, así que lo que queda al terminar es un *diff*: la lista de líneas que cambiaron entre el estado anterior del repositorio y el actual. Solo sirve si el punto de partida estaba limpio, y por eso `git status --porcelain` tiene que salir vacío antes de la petición.

La orden habitual para ver qué archivos cambiaron deja fuera los nuevos:

```bash
git diff --stat
```

```text
 package.json   |  4 +++-
 src/pedidos.js | 10 ++++++++++
 2 files changed, 13 insertions(+), 1 deletion(-)
```

La sesión había creado además `src/util/fecha.js`. `git diff` sin argumentos compara el árbol de trabajo con el índice, el área donde se preparan los cambios del siguiente commit<Cite n={27} />. Un archivo nuevo todavía no está en el índice, así que no aparece. Añadir todo al índice antes de mirar corrige la lista:

```bash
git add -A && git diff --cached --stat
```

```text
 package.json      |  4 +++-
 src/pedidos.js    | 10 ++++++++++
 src/util/fecha.js |  3 +++
 3 files changed, 16 insertions(+), 1 deletion(-)
```

`git add -A` añade al índice todo lo modificado, lo borrado y lo nuevo. `--cached` compara el índice con el último commit, y `--stat` resume por archivo. El que faltaba importa una dependencia nueva declarada en `package.json`, y la petición no pedía ninguna. Una dependencia entra en el archivo de bloqueo, se instala en cada despliegue y hay que actualizarla.

Tres cosas se leen antes que el resto. Los archivos que la petición no nombraba. Las líneas borradas, porque un agente que reescribe una función entera puede quitar una comprobación necesaria. Y los cambios en la configuración, el `Dockerfile` y la integración continua, que deciden lo que se ejecuta fuera de la máquina.

Compilar tampoco es ejecutar. Un cambio puede pasar el linter y no hacer lo que la petición pedía, así que la última comprobación es ejecutar el programa por la ruta que toca el cambio. `/diff` enseña lo mismo dentro de la sesión, incluidas las ediciones del agente<Cite n={21} repeat />.

<Callout kind="riesgo" title="Descartar una sesión entera son dos órdenes, y las dos borran">
	`git reset --hard` devuelve al último estado confirmado todo lo que git ya sigue, y `git clean -fd` borra los archivos que todavía no están en el índice. Lo que quitan no está en el historial, así que no se recupera. Ejecutarlas exige haber comprobado antes que el trabajo propio ya estaba confirmado.
</Callout>

**Cómo se comprueba.** Se ejecuta `git add -A && git diff --cached --stat` y se compara esa lista con la petición. Cada archivo que sobra se lee entero antes de continuar.

## 14. Configurar el entorno entero en un paso

Todo lo anterior se puede montar a mano, archivo por archivo. Hay un prompt que lo hace el agente, en cualquier herramienta que lo reciba. Se copia con el botón **Copiar prompt** que aparece bajo **Configurar entorno**, se pega en una sesión abierta en la raíz del proyecto, y el agente sigue once fases:

1. **Reconoce el proyecto** sin escribir nada: su herramienta, los modelos que ofrece clasificados en tres niveles, el lenguaje, las órdenes reales de pruebas, linter, tipos y auditoría, y cómo autentica y autoriza el proyecto.
2. **Propone y espera**: presenta los archivos que va a crear y el modelo de cada subagente, y se detiene hasta recibir confirmación. Incluye también las herramientas recomendadas, cada una con lo que envía fuera de la máquina.
3. **Escribe `AGENTS.md`** con las órdenes comprobadas, las convenciones, una sección opcional de vocabulario del dominio y qué skill o agente usar en cada situación.
4. **Bloquea la lectura de secretos** con la regla de permisos de su herramienta, y lo comprueba intentando leer `.env`.
5. **Crea cuatro skills de método**. `aclarar` entrevista al usuario por rondas antes de construir, con la respuesta que recomienda el agente en cada pregunta. Lo que se averigua en el código lo busca el agente, y las decisiones son del usuario. `pruebas-primero` y `depurar` fijan el ciclo de la prueba que falla y la búsqueda de la causa raíz. `orquestar` decide cuántos subagentes lanzar, con qué nivel de modelo, y cuándo usar árboles de trabajo y workflows.
6. **Crea cuatro revisores**. El de seguridad lleva un archivo de contexto del proyecto y nueve listas por dominio que carga según lo que toque el cambio. El de calidad se centra en duplicación, imports, estructura y en si el cambio hace lo que se pidió, con lo que falta y lo que sobra. El de errores y tipos busca fallos silenciosos, `catch` que ocultan errores, respaldos engañosos, estados imposibles y conversiones forzadas. El de pruebas es la rutina que ejecuta y mide.
7. **Crea seis agentes de trabajo**, cada uno con su nivel de modelo. `explorador` localiza y explica código con un modelo pequeño. `arquitecto` diseña y parte el trabajo en piezas con un modelo mayor. `implementador` resuelve una pieza en su propio árbol de trabajo con un modelo intermedio. `resolutor-compilacion` devuelve la compilación, los tipos y el linter a verde con el cambio mínimo, también con un modelo intermedio. `documentador` pone al día la documentación con un modelo pequeño. `limpiador` quita código muerto y duplicación a petición, con un modelo intermedio.
8. **Crea la skill `revisar-cambio`**, que lanza seguridad, calidad y errores en paralelo, pruebas al final, y compone el veredicto.
9. **Propone ajustes opcionales**: el modelo por omisión de los subagentes, el tamaño de los workflows, la rama base de los árboles de trabajo y tres hooks. Los hooks formatean, protegen los archivos sensibles y bloquean órdenes destructivas como `git push --force`, `git reset --hard` o `rm -rf`.
10. **Propone tres herramientas y dos colecciones de skills opcionales**, y pregunta antes de instalar cada una: graphify, claude-council, archify, las skills de Matt Pocock y gstack.
11. **Comprueba y cierra**: siembra en una rama temporal un fallo para cada uno de los cuatro revisores, comprueba que cada uno lo detecta y borra la rama. Pide al arquitecto el plan de una tarea de ejemplo. Repite la comprobación de las herramientas instaladas.

En un proyecto de prueba en Node.js, el prompt dejó esta estructura. `.claude/agents` guarda los once subagentes: los cuatro revisores, los seis agentes de trabajo y un sustituto del explorador propio de Claude Code. `.claude/skills` guarda las nueve skills, y la raíz, `AGENTS.md` y el `CLAUDE.md` que lo importa.

El texto completo se lee con **Ver el prompt completo**, bajo el botón, y es exactamente lo que se copia. De las que tienen licencia CC BY-SA se toman ideas, no texto.

Entonces `/revisar-cambio` aparece al escribir `/` y la lectura de `.env` devuelve el bloqueo. `git status --porcelain` enseña solo los archivos que el agente propuso en la fase 2.

## 15. Herramientas que se pueden añadir

Además de lo que crea, el prompt propone tres herramientas y dos colecciones de skills, todas opcionales.

**graphify** convierte el repositorio en un grafo de conocimiento: qué función llama a cuál, qué módulo importa a cuál y qué archivos forman un subsistema. El agente lo consulta antes de abrir archivos uno por uno, por ejemplo para ubicar todo lo que usa una función antes de cambiar su firma. El código se analiza en local con tree-sitter, un analizador de sintaxis, sin modelo de lenguaje, y la documentación, los PDF y las imágenes sí se envían al modelo del asistente. Construir el grafo desde la terminal, con `graphify update .`, no envía nada fuera de la máquina<Cite n={33} />.

**claude-council** es un plugin de terceros para Claude Code que hace la misma pregunta a varios modelos y muestra las respuestas lado a lado, con una síntesis de acuerdos y desacuerdos. Sirve para decisiones de diseño en las que el sesgo de un solo modelo puede engañar, por ejemplo elegir entre dos estructuras de datos posibles. Con proveedores por API, como OpenAI, Gemini o Grok, se envían a esos terceros la pregunta y hasta cinco archivos del proyecto que el plugin añade solo. El modo `--local`, con subagentes de Claude, y el modo `ollama` no envían nada fuera de la máquina<Cite n={34} />.

**archify** es una skill con una herramienta de línea de órdenes en Node.js que convierte una descripción o un repositorio en un diagrama interactivo, en un único archivo HTML autónomo. Hay cinco tipos: arquitectura, flujo de trabajo, secuencia, flujo de datos y ciclo de vida. Sirve para ver cómo se conectan las piezas de un proyecto, incluido el código que escribió el agente, y valida el diagrama antes de entregarlo. No envía datos del proyecto, y cada unas 72 horas hace una comprobación opcional de versiones nuevas en la que el servidor solo ve la IP y la hora<Cite n={35} />.

Las skills de **Matt Pocock**, `mattpocock-skills`<Cite n={31} repeat />, entrevistan antes de construir, aplican pruebas primero, depuran y revisan un cambio contra los estándares del repositorio y lo que pedía la tarea. Sus skills `tdd`, `diagnosing-bugs`, `code-review` y `grill-me` se solapan con las que crea este prompt, así que al instalarlas el prompt propone quedarse con una de cada par. Son instrucciones en Markdown y no envían nada por sí mismas. Aportan además lo que el prompt no tiene: convertir una conversación en una especificación o en tareas, con `to-spec` y `to-tickets`. `improve-codebase-architecture` mejora la arquitectura del código ya existente, y `handoff` pasa el trabajo a otra sesión.

**gstack**<Cite n={32} repeat /> es un proceso de desarrollo completo con unas cuarenta skills, para planificar, revisar, probar en un navegador, publicar y hacer retrospectivas. Se instala para todo el usuario, necesita Bun, y su instalación compila un navegador propio y registra un hook en la configuración global `~/.claude/settings.json`. En modo equipo añade otro hook que descarga y reinstala la última versión al abrir cada sesión, como mucho una vez por hora. Por eso el prompt lo propone sin modo equipo, con la telemetría apagada y sin importar las cookies del navegador, que darían al agente las sesiones iniciadas del usuario.

**Cómo se hace.** La fase 10 del prompt propone las tres herramientas y las dos colecciones una a una, y solo instala cada una si el usuario confirma.

## Qué cabe esperar de los resultados

La velocidad que se percibe y la que se mide no coinciden, y hay un experimento que separó las dos. METR repartió al azar 246 tareas entre permitir y prohibir las herramientas de IA. Los 16 participantes eran desarrolladores de proyectos maduros de código abierto, con una media de cinco años en esos mismos repositorios. Antes de empezar preveían terminar un 24 % antes con las herramientas. Al acabar el estudio estimaban haber terminado un 20 % antes. La medición dio lo contrario: un 19 % más de tiempo<Cite n={36} />.

Ese resultado describe a desarrolladores expertos sobre código que ya conocían, con las herramientas del primer semestre de 2025, y no se traslada a cualquier otra situación. Lo que sí se traslada es la distancia entre las tres cifras: la impresión de haber avanzado no sirve para decidir si se avanzó.

La encuesta de Stack Overflow de 2025, con 49 009 respuestas de 177 países, mide la dificultad sobre una población mucho más amplia. La frustración más citada con las herramientas de IA, con un 66 %, es que la solución está «casi bien, pero no del todo». Un 45,2 % añade que depurar el código generado lleva más tiempo<Cite n={37} />.

Las dos cifras apuntan al mismo sitio. Un resultado casi correcto compila y se lee bien, así que el trabajo se desplaza de escribir a comprobar. El tiempo que se ahorra escribiendo se pierde cuando no hay una comprobación barata que ejecutar.

## Por dónde seguir

La comprobación va primero, porque sin ella no hay forma de saber si lo demás funciona. Un archivo de instrucciones, una skill y un revisor se amortizan con la repetición. Se escriben cuando algo ya se ha repetido, o se generan de una vez con el prompt del punto 14 y se ajustan después.

Quedan dos cosas por aprender y las dos tienen su propio artículo. La primera es qué buscar en el código que sale. Los fallos de seguridad que más se repiten están en [siete cosas que revisar en el código que genera tu IA](/es/blog/revisar-codigo-generado-por-ia), cada uno con su corrección y la orden que la comprueba.

La segunda es cómo conseguir que la revisión se ejecute sola en cada cambio en lugar de depender de que alguien la recuerde. Ese es el asunto de [cómo pedirle a la IA código seguro](/es/blog/codigo-seguro-con-ia).
