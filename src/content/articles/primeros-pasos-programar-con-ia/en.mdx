A coding agent is a language model with tools to read files, edit them and run commands. Around it sits a program that executes those tools and hands the result back. That is the difference from a chat: a chat replies with text somebody has to apply, and an agent applies the change to the repository.

What changes for the person writing the code is the distribution of the work, not its volume. Typing each line stops being the main task, and three others take its place: deciding what has to be built, giving the agent a way to check whether it got there, and reviewing what it wrote.

This guide assumes the reader can program and is only starting to use AI to do it. Each section explains one concept with a real example, what each part of that example does, and the steps to apply it in your own project. At the end there is a prompt, copied with one button, that sets up the whole environment: project instructions, permissions, skills, four reviewers and six work agents. The same prompt proposes optional tools and skill collections.

The examples run Claude Code in the terminal. It installs with the native installer its documentation publishes. From there it opens by entering the project directory and running `claude`, which asks for a login the first time<Cite n={1} />. The same tool exists as a VS Code and JetBrains extension, as a desktop app and in the browser, and all of them share one engine and one configuration<Cite n={1} repeat />. In Cursor the agent ships inside the editor and there is nothing separate to install.

Versions measured: Claude Code 2.1.283, git 2.49.0, Node.js 24.19.0 and npm 11.8.0, on 26 September 2026. The Cursor documentation was read on 8 September 2026. All the code is rebuilt for this article.

## 1. What an agent does that a chat does not

There are three ways to use a language model to write code, and they differ in who applies the change.

**Autocomplete** proposes the end of the line being typed, inside the editor. Each suggestion is accepted or rejected by hand, so control is total and the reach is one function at most.

**Chat** takes a question and returns text. The code it produces has to be copied into the project by hand, adapted to the real names and checked for compilation. The model has not seen the repository, so it invents whatever structure looks reasonable.

**An agent** takes a task, decides which files to read, reads them, writes the changes and runs commands to check them. The Claude Code documentation defines that work as the one where the AI reads files, runs commands and makes changes autonomously while somebody watches, redirects or steps away. It contrasts it with chat assistants, which only respond with text you have to apply yourself<Cite n={2} />.

What turns a model into an agent is the tools. A **tool** is an action the model can ask for: read a file, edit it, run a shell command, search the project. The same documentation puts it plainly: without tools, the model can only respond with text<Cite n={2} repeat />.

The three ways coexist in the same working day. Autocomplete is still the fastest way to finish a line. Chat answers a question that does not touch the repository, and the agent handles tasks that cross several files.

**How to check it.** An agent session shows the tool calls before the answer: which file it read, which command it ran, what came back. In Claude Code the full detail toggles with `Ctrl+O`, which opens the transcript viewer<Cite n={3} />. If the whole session was text, it did not act as an agent.

## 2. The loop is the whole definition

An agent does not answer once. It repeats a cycle until it considers the task finished, and the documentation describes it in four steps: gather context, take action, verify the result, and repeat. Each tool use returns information that decides the next step<Cite n={2} repeat />.

An example on a simple task. The agent looks for the file to touch, reads it, writes the change, runs the tests, reads the failure they return, fixes it and runs them again. That is six tool calls for something a chat would have answered once.

The model is not what runs those tools. The model only produces text, including the request to use a tool. Around it a program interprets that request, executes it against the filesystem or the terminal and returns the output. That program is called the *harness*, and the documentation defines it as the tools, context management and execution environment that turn a model into an agent<Cite n={2} repeat />.

Cursor describes its agent with the same three pieces: the instructions that guide its behaviour, the tools for editing, searching and running commands, and the model chosen for the task<Cite n={4} />. That is why choosing a model and choosing a tool are two separate decisions.

**How to check it.** Run a task and count the tool calls before the final answer. An agent that solved something without reading a single file wrote it from memory.

## 3. The context window and the `/context` command

The **context window** is the session's working memory: the conversation history, the files read, command output, the project instructions file and the system instructions<Cite n={2} repeat />. The agent knows nothing that is not in there. It is measured in **tokens**, the unit the model counts text in, which for Claude is roughly 3.5 characters of English<Cite n={5} />.

`/context` shows how it is split. This is its output, trimmed, on opening a new session in a repository with a 29-token project instructions file and a 96-token personal one:

```text
**Tokens:** 19k / 1m (2%)

| Category                | Tokens | Percentage |
|-------------------------|--------|------------|
| System prompt           | 2.3k   | 0.2%       |
| System tools            | 4.6k   | 0.5%       |
| MCP server instructions | 686    | 0.1%       |
| Custom agents           | 374    | 0.0%       |
| Memory files            | 125    | 0.0%       |
| Skills                  | 9.9k   | 1.0%       |
| Messages                | 1k     | 0.1%       |
| Free space              | 948k   | 94.8%      |
| Autocompact buffer      | 33k    | 3.3%       |
```

Every row is something paid for in every request of the session:

- **System prompt** and **System tools**: the tool's fixed instructions and the description of its tools. They do not depend on the project.
- **MCP server instructions**: what the connected external tool servers add. They are covered in section 11.
- **Custom agents** and **Skills**: the description of each installed subagent and skill, not its full content.
- **Memory files**: the project and user instruction files from section 8.
- **Messages**: the conversation. This is the row that grows with every file read and every command run.
- **Autocompact buffer**: space reserved for summarising the conversation when the window fills up.

That automatic summary is called **compaction**. It drops old tool output first and then summarises the rest; the instructions file is re-read from disk, and anything said only in the conversation can be lost<Cite n={2} repeat />. Since the whole conversation travels with every request, a long session also costs more<Cite n={6} />.

**How to do it.**

1. Run `/context` when the session opens and note the total.
2. When a task is done, `/clear` starts a new conversation with an empty context before the next one.
3. If a long task gets close to the limit, `/compact` summarises the conversation at that point, and takes an instruction: `/compact keep the list of files touched`.
4. Whatever has to survive compaction goes in the instructions file, not in a message.

**How to check it.** Run `/context` before and after the first task. The difference in **Messages** is what that task cost, and it is the figure that says when to close the session.

## 4. Which tasks suit an agent

A task suits an agent when there is a command that decides whether it is done. The documentation calls that the **verification loop**: the agent gets a check it can run, a test, a build or a comparison, and iterates until it passes. Without one, the only thing that decides the agent is done is the agent<Cite n={2} repeat />.

| Suits it | Command that decides the end |
|---|---|
| Fixing a bug reproduced by a test | the test passes |
| Migrating a library call across twenty files | the project builds |
| Writing tests for code that has none | the tests pass, and fail when the code is broken |
| Clearing linter warnings | the linter finishes with no warnings |

Tasks without such a command suit it badly: deciding the architecture of a new module, tuning a visual design with no reference image, or anything whose criterion is that someone likes it. There the agent helps explore alternatives, and the decision stays with the person programming.

<Callout kind="nota" title="A task without a check can be split into two that have one">
	"Improve the performance of the orders screen" has no criterion. "Write a measurement that prints the current query time" does. "Get that time under 200 ms without changing the result" does too, and the agent can run both.
</Callout>

The condition can be declared with `/goal`. At the end of each turn a small model checks whether it holds, and while it does not, the agent starts another turn instead of handing control back<Cite n={7} />.

```text
/goal all tests in test/auth pass and the linter finishes with no warnings, or stop after 20 turns
```

Each part of that line has a job. "All tests in test/auth pass" is the measurable end state. "The linter finishes with no warnings" is a constraint that cannot be broken along the way. "Or stop after 20 turns" bounds how long it runs. The evaluator runs nothing itself: it judges what the agent has written in the conversation, so the condition has to be provable with a command's output<Cite n={7} repeat />. `/goal clear` removes it early.

**How to check it.** Before writing the request, name the command that will decide whether it is done. If none comes to mind, the task is not ready for an agent yet.

## 5. How to write the first request

The agent solves the statement it receives, so the statement has to carry the condition that will be checked afterwards. "Add order cancellation" does not carry it. This request does:

```text
In src/orders.js, add cancelOrder(orders, id).
Return null if the order does not exist.
If it exists, set status to 'cancelled' and return the order.
Do not add dependencies.
Criterion: node --test passes with both tests in tests/orders.test.js.
```

What each line does:

- **The file** bounds where the change goes and saves the agent reading half the repository to find it.
- **The behaviour in each case** gives the result something to be checked against, error case included.
- **The constraint** settles up front a decision the agent would otherwise make on its own.
- **The criterion** names the command that decides the end and the result it has to return.

On top of that goes what the model cannot work out from the code, such as the package manager version. In the first session it goes in the request; section 8 covers where it is stored so it never has to be repeated.

In **plan mode** the agent reads, searches and runs exploration commands, but does not edit the code: it presents a plan and waits for approval<Cite n={2} repeat />. The first review happens on a short text, and a wrong approach is corrected without reverting files.

**How to do it.**

1. Type `/plan` followed by the request, or press `Shift+Tab` until the status bar shows `plan mode on`<Cite n={8} />.
2. Read the plan. If it names files the request did not ask to touch, reply correcting it.
3. With the plan approved, the agent leaves plan mode and applies the changes.

**How to check it.** The request contains a runnable command and the result that command has to return. If it does not, deciding whether the change is finished means reading all of it.

## 6. How to stop, redirect and undo

An agent works over several turns, so it has to be stoppable halfway and reversible. There are three mechanisms and they cover different things.

| Mechanism | What it does | When to use it |
|---|---|---|
| `Esc` | Stops the response or tool in progress and keeps what was done so far | the agent is going the wrong way and a correction is enough |
| `/rewind` or `Esc` `Esc` | Opens the checkpoint menu | a whole batch of edits has to go |
| git | Returns the repository to a commit | everything the other two do not cover |

`Ctrl+C` also interrupts; with nothing running, the first press clears the input and the second exits<Cite n={3} repeat />.

Claude Code captures the state of the code before each request, and calls each capture a checkpoint. It keeps the 100 most recent in the session<Cite n={9} />. `/rewind` lists the requests sent, and on the one chosen it offers up to four actions; the two that restore code only appear if there were edits after that point<Cite n={9} repeat />:

- **Restore code and conversation**: returns both the code and the conversation to that point.
- **Restore conversation**: goes back to that message and leaves the code as it is.
- **Restore code**: undoes the file changes and keeps the conversation.
- **Summarize from here**: summarises the conversation from that point to free context.

<Callout kind="riesgo" title="A checkpoint does not cover what the terminal did">
	Tracking only reaches edits made with the agent's file tools. Files changed by a shell command, such as `rm`, `mv` or `cp`, cannot be undone from the menu. Edits by a subagent are generally not restored either, nor are changes made outside the session. The documentation states it: checkpoints are for recovery within a session and do not replace version control<Cite n={9} repeat />.
</Callout>

**How to do it.**

1. Before the request, `git status --porcelain` has to print nothing; if it does, commit or stash what is pending.
2. If the agent drifts, `Esc` and a sentence correcting it.
3. If the whole result has to go, `/rewind`, pick the request and **Restore code**.
4. Then run `git status --porcelain` again.

**How to check it.** If the last step still shows modified files, they are the ones the menu does not cover, and git discards them.

## 7. Using the agent to learn, not only to produce

An agent that writes the code leaves out the part of the work where the learning happens. Three ways of asking for the same thing keep it, and all three are ordinary requests:

| Instead of | Ask | What you get |
|---|---|---|
| "Fix the validation bug" | "In plan mode, explain which files are involved and why it fails" | the explanation over the real code, with no changes |
| "Add validation to the endpoint" | "Where is the request body validated, and in which file does the path start" | a map that serves the next tasks |
| "Write the function" | "Review my version against error handling, edge cases and naming" | the difference between the two versions |

Asking where something is happens to be what an agent answers best, because it can search instead of guessing. What it says about a library or a standard gets checked against that library's documentation, because it says it with the same confidence whether it knows or assumes.

**How to check it.** After an explanation, close the session and rebuild what was explained without it. Whatever cannot be rebuilt is what needs reading again.

## 8. The instructions file: `AGENTS.md` and `CLAUDE.md`

Every session starts with an empty context window. The **instructions file** fixes that: it is written once and the tool loads it at the start of every session.

`AGENTS.md` is the name several tools read. Claude Code reads it directly from version 2.1.277, as long as the repository has no `CLAUDE.md`; if it has one, it reads only `CLAUDE.md`, which can import `AGENTS.md` with an `@AGENTS.md` line<Cite n={10} />. There is also a personal file at `~/.claude/CLAUDE.md` for preferences across every project, and all the files found are added together in the context<Cite n={10} repeat />.

A complete file for a small project:

```markdown
# orders

## Commands
- Install: npm ci
- Tests: node --test
- Single test: node --test tests/orders.test.js
- Lint: npx eslint .

## Environment
- Node.js 24, npm 11. ES modules.

## Conventions
- Dates are stored in UTC and formatted only in the UI.
- Functions in src/ do not write to the console; they return the error.

## Before calling a task done
1. node --test exits 0.
2. npx eslint . finishes with no warnings.
3. No dependency was added that the task did not ask for.
```

What each block does:

- **Commands**: the agent does not have to guess how tests run or which manager installs. The single-test command saves running the whole suite on every iteration.
- **Environment**: what cannot be worked out with certainty by reading the code.
- **Conventions**: project decisions the code does not explain.
- **Before calling a task done**: the verification loop from section 4, written once for every task.

What stays out is what the agent can read from disk: the directory listing or the dependency list. The documentation recommends staying under 200 lines, because a longer file costs context and lowers adherence, and asks for checkable instructions: "use 2-space indentation" rather than "format the code well"<Cite n={10} repeat />.

These instructions are context, not enforced configuration. Whatever has to happen every time at a fixed point, such as formatting after every edit, is set up as a *hook*: a command the tool runs at that point of the cycle without asking the model<Cite n={10} repeat />.

**How to do it.**

1. `/init` analyses the project and generates a first `CLAUDE.md`. If the project already uses `AGENTS.md`, write there instead.
2. Run every command the file names and delete any that does not work.
3. Add the conventions and the "before calling a task done" list.
4. `/memory` opens the instruction files for editing later on.

**How to check it.** `/context all` lists the loaded files under **Memory Files**, with their path and tokens. If the file is not there, the agent is not reading it.

## 9. What is not always needed goes in a skill

The instructions file loads in full in every session, so everything added to it is paid for in every task. For what is needed only sometimes there are two mechanisms that load on a condition.

**Path rules** are files in `.claude/rules/` with a `paths` header, and they only enter the context when the agent works on a matching file<Cite n={10} repeat />:

```markdown
---
paths:
  - "src/api/**/*.ts"
---

- Every endpoint validates its input before using it.
- Errors use the standard response format.
```

A **skill** is a folder with a `SKILL.md` file holding instructions, knowledge or a procedure. When the session opens only its description loads; the full content comes in when a request matches that description or when it is invoked with `/name`<Cite n={11} />.

```markdown
---
name: change-summary
description: Summarises uncommitted changes and flags anything risky. Use it when asked what changed or for a commit message.
disable-model-invocation: false
---

Current changes:

!`git diff HEAD --stat`

Summarise those changes in two or three points, then list the risks:
missing error handling, hard-coded values or tests to update.
If there are no changes, say so.
```

What each piece does:

- **`name`**: the command name, `/change-summary`. Lowercase letters, digits and hyphens, matching the folder<Cite n={12} />.
- **`description`**: the only text the agent uses to decide whether to load it on its own. It says what it does and when to use it, in the words someone would type when asking.
- **`disable-model-invocation`**: with `true`, the skill only runs when someone types its command, never on the agent's own decision<Cite n={11} repeat />.
- **`` !`command` ``**: runs before the skill is sent to the model, and its output replaces the line<Cite n={11} repeat />.
- **The body**: the instructions, which enter the conversation as a single message.

Another useful variable is `$ARGUMENTS`, replaced by whatever is typed after the command: with `/fix-issue 123`, the body receives `123`<Cite n={11} repeat />.

The format does not belong to one tool. Skills follow the Agent Skills open standard, which makes `name` and `description` required and `license`, `compatibility`, `metadata` and `allowed-tools` optional<Cite n={12} repeat />. `disable-model-invocation` is a Claude Code extension.

**How to do it.**

1. Create `.claude/skills/change-summary/SKILL.md` for this project, or put it under `~/.claude/skills/` for every project on the machine<Cite n={11} repeat />.
2. Paste the example and adjust the description to how the team would ask for it.
3. Open a new session, because descriptions are read at start-up.

**How to check it.** Type `/` in the session and the skill has to appear in the list. Then make a request that matches its description without naming it, and check whether it loaded on its own. If it does not, the problem is the description.

## 10. Subagents: reviewers with their own context

A **subagent** is a specialised assistant that runs in its own context window, with its own instructions and tools. It does not see the main conversation, and when it finishes it returns only its summary<Cite n={13} />. That makes it useful for review: the reviewer does not carry the reasoning of whoever wrote the change.

It is defined in a Markdown file in `.claude/agents/` for the project, or in `~/.claude/agents/` for every project<Cite n={13} repeat />:

```markdown
---
name: quality-reviewer
description: Reviews whether a change will be maintainable. Use it on the diff before committing.
tools: Read, Grep, Glob, Bash
model: sonnet
---

Your question is one: will this change hold up?
Look for functions the project already has that the change reimplements,
unused imports or ones that cross a layer, and functions that
do several things at once.
Every finding carries file:line, the concrete failure and what you ran to check it.
Zero findings is a valid result.
```

What each field does:

- **`name`** and **`description`**: required. The description decides when the main agent hands it the work<Cite n={13} repeat />.
- **`tools`**: the tools allowed. A reviewer does not need to edit, so it gets neither `Edit` nor `Write`.
- **`model`**: the model it uses; `inherit` takes the session's.
- **The body**: its instructions, which replace the tool's own.

A useful review splits across four subagents with one question each. The **security** one asks whether the change lets someone do or see what they should not. The **quality** one, whether the change leaves the code better or worse: duplication, imports, structure. The **errors and types** one asks whether an error can pass unnoticed, or whether the types allow a state that should not exist. The **tests** one is the routine: it runs the suite, types and linter, measures whether the tests would fail if the code broke, and runs whatever the security one needs checked. A single reviewer with all four questions splits its attention and returns a long list of minor warnings.

What separates a useful reviewer from a noisy one is what it demands of each finding, and several public sources write it down. Cloudflare's audit guide does not accept a security finding without naming who crosses which trust boundary and what concrete result follows, and gives severity only to what is confirmed<Cite n={14} />. Anthropic's security reviewer only reports what it holds with more than 80% confidence, and explicitly discards categories that tend to be noise<Cite n={15} />. ECC requires citing the exact line, reading the code's callers and accepting that a review with no findings is valid<Cite n={16} />. Google's review guide asks reviewers not to accept changes that degrade the code health of the system<Cite n={17} />.

Each subagent spends tokens on its own model, and the `model` field decides which. If neither the call nor the definition sets it, Claude Code uses the model in the `CLAUDE_CODE_SUBAGENT_MODEL` variable and, without it, the main conversation's model<Cite n={13} repeat />. That is usually the most expensive one. A reviewer that searches files does not need the same model as one that reasons about authorisation, so each definition sets its own.

Several subagents editing the same directory at once trip over each other. Git worktrees prevent it: each subagent works in another directory on its own branch, and the main agent merges the branches one at a time. In Claude Code it is switched on with `isolation: worktree` in the subagent's definition, and by default the worktree starts from the remote's default branch, not the current one<Cite n={18} />.

Work agents split the same way reviewers do, each with its own model tier. `explorer` and `doc-writer` use a small model: the first locates and explains code, the second writes documentation. `architect` uses a top model to design the change and split it into pieces. `implementer` builds one piece in its own worktree, with a mid model. `build-fixer`, at the same tier, gets the build, the types and the linter back to green with the smallest change. `cleaner` completes the group: dead code and duplication, on request, also at the mid tier. Only the main agent launches them, and it merges their branches one at a time.

A workflow takes the same idea to another scale: a script that launches dozens of subagents in stages. Claude Code warns when one schedules more than 25 agents, and accepts a size guideline that aims for fewer than 5, 10 or 50<Cite n={19} />.

**How to do it.**

1. Create `.claude/agents/quality-reviewer.md` with the example.
2. Run it by naming it: `@agent-quality-reviewer review the current diff`<Cite n={13} repeat />.
3. The four reviewers, the six work agents and the `review-change` skill that runs the review are created by the prompt in section 14.

**How to check it.** Introduce two quality bugs on purpose, a utility that already exists reimplemented and an unused import, and run the reviewer. If it does not flag them, its instructions are not enough.

## 11. Plugins install what someone else already wrote

A **plugin** is an installable package that bundles skills, agents, *hooks* and MCP servers<Cite n={20} />. **MCP**, short for Model Context Protocol, is an open protocol for connecting a model to external data sources and tools<Cite n={5} repeat />. An MCP server adds new tools to the agent, for Slack, Jira, a database or a browser.

Plugins are distributed through catalogues called *marketplaces*. Anthropic's official one, `claude-plugins-official`, is registered the first time an interactive session opens, so installing from it takes a single command<Cite n={20} repeat />:

```shell
/plugin install commit-commands@claude-plugins-official
```

`commit-commands` is the plugin's name, which adds commands for committing, pushing and opening pull requests, and what follows `@` is the catalogue it comes from. A third-party catalogue is registered first with `/plugin marketplace add <owner>/<repo>`, which installs nothing<Cite n={20} repeat />. `/plugin` with no arguments opens the panel of catalogues, installed plugins and load errors, and `/mcp` manages connections to MCP servers<Cite n={21} />.

Before installing, each plugin's details show two things. **Context cost** is what it adds to every message, and what its skills and agents add once loaded. **Will install** lists the commands, agents, skills, *hooks* and servers it brings<Cite n={20} repeat />. The first is paid in every session, including the ones that never use the plugin.

Code intelligence plugins connect a language server, the technology that gives an editor go-to-definition. With one installed, the agent sees the type errors its own edits introduce before any build. The plugin does not include the server, which is installed separately<Cite n={22} />.

<Callout kind="riesgo" title="A plugin runs code with the permissions of whoever installs it">
	The documentation states it without qualification: an installed plugin can execute arbitrary code on the machine with the user's privileges. Anthropic adds that it does not control what servers, files or other software a plugin includes, and cannot verify that it works as intended<Cite n={23} />. Before installing a third-party plugin, open its repository and read what it brings.
</Callout>

**How to check it.** Run `/context` before and after installing. A plugin that adds context every turn and never gets used gets uninstalled.

## 12. What permissions it gets

An agent runs commands and reads files, so there are two decisions before the first long session: what it stops to ask about, and which files it can read.

The first is set by **permission modes**, cycled with `Shift+Tab` and shown in the status bar<Cite n={8} repeat />:

| Mode | What it does |
|---|---|
| `default` | Asks the first time each tool is used. The status bar shows it as `manual mode on`. |
| `acceptEdits` | Accepts edits and basic file commands inside the project without asking. |
| `plan` | Reads and explores, but does not edit the code. |
| `auto` | Approves tool calls with background safety checks. |
| `bypassPermissions` | Skips permission prompts. |

The last one is what gets switched on the first day to stop answering questions. Its documentation restricts it to isolated environments, containers or virtual machines where the agent cannot cause damage<Cite n={24} />.

The second matters because the agent sends the content of the files it reads to the provider's server, and a `.env` with credentials goes out in that request like any code. The exclusion is declared in `.claude/settings.json`<Cite n={25} />:

```json
{
	"permissions": {
		"deny": ["Read(./.env)", "Read(./.env.*)"]
	}
}
```

`deny` is the list of actions the tool always refuses. `Read(./.env)` is the read tool on that exact file, and `Read(./.env.*)` covers `.env.local`, `.env.production` and the rest. Being in `.gitignore` does not protect the file: measured without the rule, the read tool returned it with no error. With the rule, it returns the block:

```text
File is in a directory that is denied by your permission settings.
```

The rule also reaches shell commands that name the file, such as `cat .env` or `head .env`. It does not reach a script that opens the file itself, such as a Node or Python program<Cite n={24} repeat />.

Cursor starts from a different place. It ignores what `.gitignore` lists plus a built-in list that includes `.env*` by default, and anything else is excluded in `.cursorignore`. The same documentation notes that the agent's terminal and external tools cannot block access to what that file covers<Cite n={26} />.

In both tools the exclusion lives in configuration, not in the instructions file. Permission rules are enforced by the tool, not the model<Cite n={24} repeat />, so a line in `AGENTS.md` saying "do not read `.env`" does not change what the tool allows.

One cost decision remains: which model the session uses. It changes with `/model`, and the documentation recommends starting with Sonnet, which handles most coding tasks well and costs less than Opus<Cite n={6} repeat />.

**How to check it.** Ask the agent for the contents of `.env`. With the rule in place, the tool returns the block instead of the file. The model replying that it will not do it checks nothing, because the rule did not produce that reply.

## 13. How to review what it did

An agent edits files directly, so what is left when it finishes is a *diff*: the list of lines that changed between the previous state of the repository and the current one. It is only useful if the starting point was clean, which is why `git status --porcelain` has to print nothing before the request.

The usual command to see which files changed leaves out the new ones:

```bash
git diff --stat
```

```text
 package.json  |  4 +++-
 src/orders.js | 10 ++++++++++
 2 files changed, 13 insertions(+), 1 deletion(-)
```

The session had also created `src/util/date.js`. `git diff` with no arguments compares the working tree with the index, the area where the next commit's changes are staged<Cite n={27} />. A new file is not in the index yet, so it does not show up. Adding everything to the index before looking fixes the list:

```bash
git add -A && git diff --cached --stat
```

```text
 package.json     |  4 +++-
 src/orders.js    | 10 ++++++++++
 src/util/date.js |  3 +++
 3 files changed, 16 insertions(+), 1 deletion(-)
```

`git add -A` stages everything modified, deleted and new. `--cached` compares the index with the last commit, and `--stat` summarises per file. The missing file imports a new dependency declared in `package.json`, and the request asked for none. A dependency enters the lockfile, installs on every deploy and needs updating.

Three things get read before the rest. Files the request did not name. Deleted lines, because an agent rewriting a whole function can drop a check that was needed. And changes to configuration, the `Dockerfile` and continuous integration, which decide what runs outside the developer's machine.

Building is not running either. A change can pass the linter and still not do what the request asked, so the last check is running the program along the path the change touches. `/diff` shows the same inside the session, including the agent's edits<Cite n={21} repeat />.

<Callout kind="riesgo" title="Discarding a whole session is two commands, and both delete">
	`git reset --hard` returns everything git already tracks to the last committed state, and `git clean -fd` deletes the files that are not in the index yet. What they remove is not in the history, so it does not come back. Running them requires having checked first that your own work is already committed.
</Callout>

**How to check it.** Run `git add -A && git diff --cached --stat` and compare that list with the request. Every file that does not belong gets read in full before continuing.

## 14. Set up the whole environment in one step

Everything above can be built by hand, file by file. There is a prompt that has the agent do it, in whichever tool receives it. Copy it with the **Copy prompt** button under **Set up environment**, paste it into a session opened at the project root, and the agent follows eleven phases:

1. **Surveys the project** without writing anything: its tool, the models it offers sorted into three tiers, the language, the real test, lint, type and audit commands, and how the project authenticates and authorises.
2. **Proposes and waits**: presents the files it will create and the model for each subagent, and stops until it gets confirmation. It also includes the recommended tools, each with what it sends off the machine.
3. **Writes `AGENTS.md`** with the checked commands, the conventions, an optional domain vocabulary section and which skill or agent to use in each situation.
4. **Blocks reading secrets** with its tool's permission rule, and checks it by trying to read `.env`.
5. **Creates four method skills**. `clarify` interviews the user in rounds before building, with the agent's recommended answer to each question. What can be found in the code, the agent looks up; the decisions belong to the user. `test-first` and `root-cause-debugging` set the failing-test cycle and the search for the root cause. `orchestrate` decides how many subagents to launch, at what model tier, and when to use worktrees and workflows.
6. **Creates four reviewers**. The security one carries a project context file and nine per-domain checklists that it loads depending on what the change touches. The quality one focuses on duplication, imports, structure and whether the change does what was asked, with what is missing and what is extra. The errors and types one looks for silent failures, `catch` blocks that hide errors, misleading fallbacks, impossible states and forced conversions. The tests one is the routine that runs and measures.
7. **Creates six work agents**, each with its own model tier. `explorer` locates and explains code with a small model. `architect` designs the change and splits it into pieces with a top model. `implementer` builds one piece in its own worktree with a mid model. `build-fixer` gets the build, the types and the linter back to green with the smallest change, also at the mid tier. `doc-writer` brings the documentation up to date with a small model. `cleaner` clears dead code and duplication on request, with a mid model.
8. **Creates the `review-change` skill**, which runs security, quality and errors in parallel, tests last, and composes the verdict.
9. **Proposes optional settings**: the default subagent model, the workflow size, the base branch for worktrees, and three hooks. The hooks format code, protect sensitive files and block destructive commands such as `git push --force`, `git reset --hard` or `rm -rf`.
10. **Proposes three tools and two skill collections, all optional**, and asks before installing each one: graphify, claude-council, archify, Matt Pocock's skills and gstack.
11. **Checks and closes**: seeds one flaw per reviewer, for all four, on a temporary branch, confirms each one catches it and deletes the branch. Asks the architect for the plan of a sample task. Repeats the check of the installed tools.

The base setup, phases 1 to 9, takes 15 to 20 minutes on a small project. In the test run it took 14: 5 to survey the project and propose, 2 waiting for the answer, and 7 to create every file. With the five optional tools and the phase 11 tests, the whole run took 29 minutes. Two things account for the difference. gstack compiles its binaries and downloads its browser, about 5 minutes. The reviewer test takes about 8, because it launches the four reviewers on planted flaws and the tests reviewer mutates the code to see whether any test catches it.

On a Node.js test project, with the five optional tools installed, the prompt left this structure. `.claude/agents` holds the ten subagents: the four reviewers and the six work agents. `.claude/skills` holds sixteen skills: the prompt's nine, graphify's and six of Matt Pocock's. The tools installed for the user (archify, gstack and claude-council) appear at the bottom, collapsed, with their path under `~/.claude`.

The prompt does not touch application code. If during setup the agent finds it needs to install a dependency, plugin or MCP server, it first proposes it with its source and reason, and waits for confirmation.

<Callout kind="riesgo" title="A prompt that creates files is read before it is pasted">
	This prompt asks the agent to run the project's commands and write configuration files. The full text opens with **Show the full prompt**, under the button, and it is exactly what gets copied. Phase 2 makes the agent stop before writing: if it carries on without asking, interrupt it with `Esc`.

The reviewers, the method skills and the work agents adapt ideas from nine public sources. For security, Cloudflare's audit guide<Cite n={14} repeat />, Anthropic's reviewer<Cite n={15} repeat /> and Trail of Bits' skills<Cite n={28} />. For quality, tests and method, Anthropic's official `pr-review-toolkit` and `feature-dev` plugins<Cite n={29} />, ECC<Cite n={16} repeat />, Google's review guide<Cite n={17} repeat />, Superpowers<Cite n={30} />, Matt Pocock's skills<Cite n={31} /> and gstack<Cite n={32} />. From the CC BY-SA sources, ideas are taken, not text.

**How to check it.** New skills and subagents register when a session opens, so close it and open it again. Then `/review-change` appears on typing `/` and reading `.env` returns the block. `git status --porcelain` shows only the files the agent proposed in phase 2.

## 15. Tools that can be added

Besides what it creates, the prompt proposes three tools and two skill collections, all optional.

**graphify** turns the repository into a knowledge graph: which function calls which, which module imports which, and which files make up a subsystem. The agent queries it before opening files one by one, for instance to find every caller of a function before changing its signature. The code is analysed locally with tree-sitter, a syntax parser, with no language model involved, while documentation, PDFs and images do get sent to the assistant's own model. Building the graph from the terminal, with `graphify update .`, sends nothing off the machine<Cite n={33} />.

**claude-council** is a third-party plugin for Claude Code that asks the same question to several models and shows the answers side by side, with a summary of where they agree and disagree. It suits design decisions where a single model's bias could mislead, such as choosing between two possible data structures. With API providers, such as OpenAI, Gemini or Grok, the question and up to five project files the plugin adds by itself go out to those third parties. The `--local` mode, using Claude subagents, and the `ollama` mode send nothing off the machine<Cite n={34} />.

**archify** is a skill with a Node.js command-line tool that turns a description or a repository into an interactive diagram, as a single self-contained HTML file. There are five types: architecture, workflow, sequence, data flow and lifecycle. It serves to show how a project's pieces connect, including code the agent wrote, and it validates the diagram before handing it over. It sends no project data, and roughly every 72 hours it runs an optional check for new versions, in which the server sees only the IP address and the time<Cite n={35} />.

**Matt Pocock**'s skills, `mattpocock-skills`<Cite n={31} repeat />, interview the user before building, apply test-first, debug and review a change against the repository's own standards and what the task asked for. Its `tdd`, `diagnosing-bugs`, `code-review` and `grill-me` skills overlap with the ones this prompt creates, so on installing them the prompt proposes keeping one from each pair. They are Markdown instructions and send nothing by themselves. They also bring what the prompt lacks: turning a conversation into a specification or into tasks, with `to-spec` and `to-tickets`. `improve-codebase-architecture` improves the architecture of existing code, and `handoff` passes the work to another session.

**gstack**<Cite n={32} repeat /> is a complete development process with roughly forty skills, for planning, reviewing, testing in a browser, publishing and running retrospectives. It installs for the whole user account, needs Bun, and its installer compiles its own browser and registers a hook in the global `~/.claude/settings.json`. In team mode it adds another hook that pulls and reinstalls the latest version whenever a session opens, at most once an hour. That is why the prompt proposes it without team mode, with telemetry off and without importing the browser's cookies, which would hand the agent the user's signed-in sessions.

**How to do it.** Phase 10 of the prompt proposes the three tools and the two collections one at a time, and only installs each one if the user confirms.

## What to expect from the results

Perceived speed and measured speed do not match, and one experiment separated the two. METR randomly assigned 246 tasks to allow or disallow AI tools. The 16 participants were developers on mature open-source projects, averaging five years on those same repositories. Before starting, they forecast finishing 24% faster with the tools. After the study they estimated they had finished 20% faster. The measurement gave the opposite: 19% more time<Cite n={36} />.

That result describes expert developers on code they already knew, with the tools of the first half of 2025, and it does not transfer to every other situation. What does transfer is the distance between the three figures: the impression of having moved faster is not enough to decide whether you did.

The 2025 Stack Overflow survey, with 49,009 responses from 177 countries, measures the difficulty across a far wider population. The most cited frustration with AI tools, at 66%, is a solution that is «almost right, but not quite». Another 45.2% add that debugging generated code takes more time<Cite n={37} />.

Both figures point the same way. An almost-correct result compiles and reads well, so the work shifts from writing to checking. The time saved writing is lost again when there is no cheap check to run.

## Where to go next

The check comes first, because without it there is no way to know whether the rest works. An instructions file, a skill and a reviewer pay off through repetition. They get written once something has already repeated, or generated in one go with the prompt in section 14 and adjusted afterwards.

Two things are left to learn and both have their own article. The first is what to look for in the code that comes out. The security failures that repeat most are in [seven things to check in the code your AI writes](/en/blog/seven-things-to-check-in-ai-generated-code), each with its fix and the command that checks it.

The second is how to get the review to run on every change by itself instead of depending on somebody remembering it. That is the subject of [how to ask AI for secure code](/en/blog/ask-ai-for-secure-code).
