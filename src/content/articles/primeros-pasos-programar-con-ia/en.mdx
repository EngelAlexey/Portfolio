A coding agent reads the repository, edits files and runs commands on its own. With one, your job becomes deciding what to build, giving the agent a check it can run and reviewing what it wrote.

The examples use Claude Code in the terminal. Install it with the native installer its documentation publishes. Then open a terminal in the project directory and run `claude`, which asks you to log in the first time<Cite n={1} />. Claude Code also exists as a VS Code and JetBrains extension, as a desktop app and in the browser. All of them work the same way and read the same configuration<Cite n={1} repeat />. In Cursor, the agent is built into the editor and needs no separate installation.

Measurements were taken on 26 September 2026 with Claude Code 2.1.283, git 2.49.0, Node.js 24.19.0 and npm 11.8.0. The Cursor documentation was read on 8 September 2026. All the code is rebuilt for the article.

Section 14 describes a prompt that sets up the whole environment in your project: instructions, permissions, skills, four reviewers and six work agents. Copy it with the **Copy prompt** button in the **Set up environment** panel.

## 1. What sets an agent apart from a chat

A language model can be used for coding in three ways, and they differ in who applies the change.

**Autocomplete** proposes the end of the line you are typing, inside the editor. You accept or reject each suggestion, so control is complete and the reach is one function at most.

**Chat** takes a question and returns text. You copy that code into the project, adapt it to the real names and check that it compiles. Since the model has not seen the repository, the code assumes a structure that may not match the real one.

**An agent** takes a task, decides which files to read, reads them, writes the changes and runs commands to check them. The Claude Code documentation defines it this way: the AI reads files, runs commands and makes changes autonomously. Meanwhile, you watch, redirect it or let it work on its own. The documentation contrasts it with chat assistants, which only respond with text you have to apply yourself<Cite n={2} />.

A model becomes an agent when it has tools. A **tool** is an action the model can ask for: read a file, edit it, run a shell command or search the project. According to the same documentation, without tools the model can only respond with text<Cite n={2} repeat />.

Each of the three has its use. Autocomplete finishes a line, chat answers questions that do not touch the repository and the agent handles tasks that span several files.

**How to check it.** In an agent session, tool calls appear before the answer: which file it read, which command it ran and what came back. In Claude Code, `Ctrl+O` toggles the transcript viewer, with the detail of every call<Cite n={3} />. If the session produced only text, it did not work as an agent.

## 2. How an agent works

An agent does not answer once. It repeats a cycle until it considers the task done. The documentation describes it in four steps: gather context, take action, verify the result and repeat. The result of each tool use decides the next step<Cite n={2} repeat />.

A **turn** is one complete response from the agent. It starts when you send a message and ends when the agent finishes responding, with as many tool calls as it needs<Cite n={2} repeat />. For example, to fix a simple bug, the agent finds the file, reads it, writes the change and runs the tests. Then it reads the failure they return, fixes it and runs them again. That is six tool calls in one turn, where a chat would have given a single answer.

The model does not run those tools. It only produces text, including the request to use a tool. A separate program interprets that request, executes it against the filesystem or the terminal and hands the output back.

That program is called the *harness*. The documentation defines it as the tools, context management and execution environment that turn a model into an agent. Claude Code is the harness, and Claude is the model working inside it<Cite n={2} repeat />.

Cursor describes its agent with three pieces. They are the instructions that guide its behaviour, the tools for editing, searching and running commands, and the model chosen for the task<Cite n={4} />. That is why choosing the model and choosing the harness are two separate decisions.

**How to check it.** Run a task and count the tool calls before the final answer. If the agent solved something without reading a single file, it wrote it from memory.

## 3. What the context window is and how to measure it

The **context window** is the text the model has available during the session. It holds the conversation history, the files read, command output, the project instructions file and the system instructions<Cite n={2} repeat />. The agent knows nothing that is not in there. Its size is measured in **tokens**, the unit the model counts text in. For Claude, a token is roughly 3.5 characters of English text<Cite n={5} />.

The `/context` command shows how it is split. This is its output, trimmed, on opening a new session in a sample repository. The project instructions file takes 29 tokens and the personal one 96:

```text
**Tokens:** 19k / 1m (2%)

| Category                | Tokens | Percentage |
|-------------------------|--------|------------|
| System prompt           | 2.3k   | 0.2%       |
| System tools            | 4.6k   | 0.5%       |
| MCP server instructions | 686    | 0.1%       |
| Custom agents           | 374    | 0.0%       |
| Memory files            | 125    | 0.0%       |
| Skills                  | 9.9k   | 1.0%       |
| Messages                | 1k     | 0.1%       |
| Free space              | 948k   | 94.8%      |
| Autocompact buffer      | 33k    | 3.3%       |
```

Apart from `Free space` and `Autocompact buffer`, every row is text sent with every request in the session:

- `System prompt` and `System tools`: Claude Code's fixed instructions and the description of its tools. They do not depend on the project.
- `MCP server instructions`: what the connected external tool servers add, covered in section 11.
- `Custom agents` and `Skills`: the description of each installed subagent and skill, not its full content.
- `Memory files`: the project and personal instruction files, covered in section 8.
- `Messages`: the conversation. This is the row that grows with every file read and every command run.
- `Autocompact buffer`: space reserved for summarising the conversation when the window fills up.

That automatic summary is called **compaction**. It drops old tool output first and then summarises the rest. The instructions file is re-read from disk, but anything said only in the conversation can be lost<Cite n={2} repeat />. The whole conversation is also sent with every request, so a long session costs more<Cite n={6} />.

**How to do it.**

1. Run `/context` when the session opens and note the total.
2. When a task is done, run `/clear` to start a new conversation, with an empty context, before the next one.
3. If a long task gets close to the limit, run `/compact` to summarise the conversation at that point. It takes an instruction: `/compact keep the list of files touched`.
4. Put whatever has to survive compaction in the instructions file, not in a message.

**How to check it.** Run `/context` before and after the first task. The difference in `Messages` is what that task took up. With that figure you can decide when to close the session.

## 4. Which tasks to give an agent

A task suits an agent when there is a command that decides whether it is done. The documentation calls that the **verification loop**. You give the agent a check it can run: a test, a build or a comparison. The agent repeats the work until the check passes. Without one, the only thing that decides the agent is done is the agent itself<Cite n={2} repeat />.

| Suits it | Command that decides the end |
|---|---|
| Fixing a bug reproduced by a test | the test passes |
| Migrating a library call across twenty files | the project builds |
| Writing tests for code that has none | the tests pass, and fail when the code is broken |
| Clearing linter warnings | the linter finishes with no warnings |

Tasks without such a command suit it badly, such as deciding the architecture of a new module or tuning a visual design with no reference image. Neither does a task whose only criterion is that someone likes the result. In those cases the agent helps explore alternatives, but the decision is yours.

<Callout kind="nota" title="A task without a check can be split into two that have one">
	"Improve the performance of the orders screen" has no criterion. "Write a measurement that prints the current query time" does. So does "get that time under 200 ms without changing the result". The agent can run both.
</Callout>

Declare that condition with `/goal`. At the end of each turn, a small model checks whether it holds. While it does not, the agent starts another turn instead of handing control back to you<Cite n={7} />.

```text
/goal all tests in test/auth pass and the linter finishes with no warnings, or stop after 20 turns
```

Each part of that line has a job. "All tests in test/auth pass" is the measurable end state. "The linter finishes with no warnings" is a constraint that has to hold throughout the work. "Or stop after 20 turns" limits how long it runs.

The evaluator runs nothing: it judges what the agent has written in the conversation. That is why the condition has to be provable with a command's output<Cite n={7} repeat />. `/goal clear` removes the condition early.

**How to check it.** Before writing the request, name the command that will decide whether the task is done. If you cannot find one, the task is not ready for an agent yet.

## 5. How to write a request

The agent solves the statement it receives, so the statement has to include the condition that will be checked afterwards. "Add order cancellation" does not include it. This request does:

```text
In src/orders.js, add cancelOrder(orders, id).
Return null if the order does not exist.
If it exists, set status to 'cancelled' and return the order.
Do not add dependencies.
Criterion: node --test passes with both tests in tests/orders.test.js.
```

What each line does:

- **The file** bounds where the change goes and saves the agent reading half the repository to find it.
- **The behaviour in each case**, error case included, gives the result something to be checked against.
- **The constraint** settles in advance something that, if the request does not say it, the agent decides on its own.
- **The criterion** names the command that decides the end and the result it has to return.

Also add what the model cannot work out from the code, such as the package manager version. In the first session, include it in the request. Section 8 explains where to store it so you do not have to repeat it.

In **plan mode**, the agent reads, searches and runs exploration commands, but does not edit the code: it presents a plan and waits for your approval<Cite n={2} repeat />. That way, the first review happens on a short text. You correct a wrong approach in that text, with no files to revert.

**How to do it.**

1. Type `/plan` followed by the request, or press `Shift+Tab` until the status bar shows `plan mode on`<Cite n={8} />.
2. Read the plan. If it names files the request did not ask to touch, correct it in your reply.
3. Approve the plan. The agent leaves plan mode and applies the changes.

**How to check it.** The request contains a runnable command and the result that command has to return. If it does not, you will have to read the whole change to decide whether it is finished.

## 6. How to stop, correct and undo the agent's work

An agent works over several turns, so you need to be able to stop it halfway through a task and go back. There are three mechanisms, and each covers a different case:

| Mechanism | What it does | When to use it |
|---|---|---|
| `Esc` | Stops the response or tool in progress and keeps what was done so far | the agent is doing something other than what you asked and one instruction is enough |
| `/rewind` or `Esc` `Esc` | Opens the checkpoint menu | a whole batch of edits has to go |
| git | Returns the repository to a commit | everything the other two do not cover |

`Ctrl+C` also interrupts. With nothing running, the first press clears the input and the second exits Claude Code<Cite n={3} repeat />.

Claude Code saves the state of the code before each request that starts a turn, and calls each capture a **checkpoint**. It keeps file snapshots for the 100 most recent checkpoints in the session<Cite n={9} />. `/rewind` lists the requests you sent and, on the one you pick, offers five actions<Cite n={9} repeat />:

1. **Restore code and conversation**: returns both the code and the conversation to that point.
2. **Restore conversation**: goes back to that message and leaves the code as it is.
3. **Restore code**: undoes the file changes and keeps the conversation.
4. **Summarize from here**: summarises the conversation from that point on to free space in the context window.
5. **Summarize up to here**: summarises the conversation before that point and keeps later messages intact.

The two code restore actions only appear if there were edits after that point. **Never mind** returns to the list without changing anything<Cite n={9} repeat />.

<Callout kind="riesgo" title="A checkpoint does not cover what the terminal did">
	Tracking only covers the edits the agent makes with its file tools. Changes made by a shell command, such as `rm`, `mv` or `cp`, cannot be undone from the menu. Edits by a subagent are generally not restored either, nor are changes made outside the session. According to the documentation, checkpoints are for recovery within a session and do not replace version control<Cite n={9} repeat />.
</Callout>

**How to do it.**

1. Before the request, run `git status --porcelain`. The output has to be empty; if it is not, commit what is pending or set it aside with `git stash`.
2. If the agent drifts from what you asked, press `Esc` and correct it with one sentence.
3. If the whole result has to go, run `/rewind`, pick the request and choose **Restore code**.
4. Then run `git status --porcelain` again.

**How to check it.** If the last step still shows modified files, they are the ones the menu does not cover. Discard them with git; section 13 explains the two commands that do it and their risk.

## 7. How to use the agent to learn

When the agent writes the code, you skip the part of the work where the learning happens. These three ways of asking keep that part, and all three are ordinary requests:

| Instead of | Ask | What you get |
|---|---|---|
| "Fix the validation bug" | "In plan mode, explain which files are involved and why it fails" | the explanation over the real code, with no changes |
| "Add validation to the endpoint" | "Where is the request body validated, and in which file does the path start" | a map that serves the next tasks |
| "Write the function" | "Review my version against error handling, edge cases and naming" | the difference between the two versions |

An agent is good at questions about where something is, because it can search the repository instead of guessing. Check against the documentation, however, anything it says about a library or a standard. The answer sounds just as sure when the fact is right as when it is wrong.

**How to check it.** After an explanation, close the session and try to rebuild what was explained without it. Whatever you cannot rebuild is what you need to read again.

## 8. How to document the project: `AGENTS.md` and `CLAUDE.md`

Every Claude Code session starts with a fresh context window, with nothing from previous conversations<Cite n={10} />. The **instructions file** holds what the agent needs to know about the project. You write it once and Claude Code loads it at the start of every session.

`AGENTS.md` is the file name several coding agents read. Claude Code reads it directly from version 2.1.277 if the repository has no `CLAUDE.md`. If it has one, by default it reads only `CLAUDE.md`, which can import `AGENTS.md` with an `@AGENTS.md` line<Cite n={10} repeat />. A personal file at `~/.claude/CLAUDE.md` also holds your preferences for every project. Claude Code adds every file it finds to the context instead of keeping just one<Cite n={10} repeat />.

This is a complete file for a small project:

```markdown
# orders

## Commands
- Install: npm ci
- Tests: node --test
- Single test: node --test tests/orders.test.js
- Lint: npx eslint .

## Environment
- Node.js 24, npm 11. ES modules.

## Conventions
- Dates are stored in UTC and formatted only in the UI.
- Functions in src/ do not write to the console; they return the error.

## Before calling a task done
1. node --test exits 0.
2. npx eslint . finishes with no warnings.
3. No dependency was added that the task did not ask for.
```

What each part does:

- **Commands**: the agent does not have to guess how tests run or which package manager installs. The single-test command saves it running the whole suite on every attempt.
- **Environment**: what cannot be worked out with certainty by reading the code.
- **Conventions**: the project's decisions that the code does not explain.
- **Before calling a task done**: the verification loop from section 4, written once for every task.

Leave out what the agent can read from disk, such as the directory listing or the dependency list. The documentation recommends staying under 200 lines, because a long file takes more context and the model follows its instructions less reliably. It also asks for instructions that can be checked: "use 2-space indentation" rather than "format the code well"<Cite n={10} repeat />.

The instructions file is context: the model reads it, but nothing forces it to comply. Set up as a *hook* whatever has to happen every time at a fixed point, such as formatting the code after every edit. A *hook* is a command Claude Code runs at that point of the cycle without asking the model<Cite n={10} repeat />.

**How to do it.**

1. Run `/init`, which analyses the project and generates a first `CLAUDE.md`. If the project already uses `AGENTS.md`, write in that file instead.
2. Run every command the file names and delete any that does not work.
3. Add the conventions and the "Before calling a task done" list.
4. To edit the instruction files later, run `/memory`.

**How to check it.** Run `/context all`. The `Memory Files` list shows the loaded files, with their path and tokens. If the file is not there, the agent is not reading it.

## 9. What path rules and skills are

The instructions file loads in full in every session, so everything you add to it takes up context in every task. For what is needed only sometimes, there are two mechanisms that load on a condition.

**Path rules** are files in `.claude/rules/` with a `paths` header. They only enter the context when the agent works on a file that matches those paths<Cite n={10} repeat />:

```markdown
---
paths:
  - "src/api/**/*.ts"
---

- Every endpoint validates its input before using it.
- Errors use the standard response format.
```

A **skill** is a folder with a `SKILL.md` file holding instructions, knowledge or a procedure. When the session opens, only its description loads. The full content comes in when a request matches that description or when you invoke it with `/name`<Cite n={11} />.

```markdown
---
name: change-summary
description: Summarises uncommitted changes and flags anything risky. Use it when asked what changed or for a commit message.
disable-model-invocation: false
---

Current changes:

!`git diff HEAD --stat`

Summarise those changes in two or three points, then list the risks:
missing error handling, hard-coded values or tests to update.
If there are no changes, say so.
```

What each part does:

- **`name`**: the command name, `/change-summary`. It uses lowercase letters, digits and hyphens, matching the folder<Cite n={12} />.
- **`description`**: the only text the agent uses to decide whether to load the skill on its own. It says what the skill does and when to use it, in the words someone would type when asking.
- **`disable-model-invocation`**: with `true`, the skill only runs when someone types its command, never on the agent's own decision<Cite n={11} repeat />.
- **`` !`command` ``**: runs before the skill is sent to the model, and its output replaces the line<Cite n={11} repeat />.
- **The body**: the instructions, which enter the conversation as a single message.

The skill also accepts the `$ARGUMENTS` variable, which is replaced by whatever is typed after the command. With `/fix-issue 123`, the body receives `123`<Cite n={11} repeat />.

The format does not belong to one product. Skills follow the Agent Skills open standard, which makes `name` and `description` required and `license`, `compatibility`, `metadata` and `allowed-tools` optional<Cite n={12} repeat />. `disable-model-invocation` is a Claude Code extension.

**How to do it.**

1. Create `.claude/skills/change-summary/SKILL.md` for this project, or put it under `~/.claude/skills/` for every project on the machine<Cite n={11} repeat />.
2. Paste the example and adjust the description to how your team would ask for it.
3. Open a new session, because descriptions are read at start-up.

**How to check it.** Type `/` in the session: the skill has to appear in the list. Then make a request that matches its description without naming it, and check whether it loaded on its own. If it does not, the problem is the description.

## 10. What subagents are and how to split a review

A **subagent** is a specialised agent that works in its own context window, with its own instructions and tools. It does not see the main conversation, and when it finishes it returns only a summary<Cite n={13} />. That makes it useful for review: the reviewer does not receive the reasoning of whoever wrote the change.

It is defined in a Markdown file, in `.claude/agents/` for the project or in `~/.claude/agents/` for all your projects<Cite n={13} repeat />:

```markdown
---
name: quality-reviewer
description: Reviews whether a change will be maintainable. Use it on the diff before committing.
tools: Read, Grep, Glob, Bash
model: sonnet
---

Your question is one: will this change hold up?
Look for functions the project already has that the change reimplements,
unused imports or ones that cross a layer, and functions that
do several things at once.
Every finding carries file:line, the concrete failure and what you ran to check it.
Zero findings is a valid result.
```

What each field does:

- **`name`** and **`description`**: both are required. The description decides when the main agent hands it the work<Cite n={13} repeat />.
- **`tools`**: the tools allowed. A reviewer does not need to edit, so it gets neither `Edit` nor `Write`.
- **`model`**: the model it uses; with `inherit`, it takes the session's.
- **The body**: its instructions, which replace Claude Code's default instructions.

The documentation recommends that each subagent focus on one specific task<Cite n={13} repeat />. That is why a useful review splits across four subagents, with one question each:

1. The **security** one asks whether the change lets someone do or see something they should not.
2. The **quality** one asks whether the change leaves the code better or worse, in duplication, imports and structure.
3. The **errors and types** one asks whether an error can pass unnoticed, or whether the types allow a state that should not exist.
4. The **tests** one does not judge the design. It runs the suite, the types and the linter, measures whether the tests would fail if the code broke and runs whatever the security one needs checked.

A useful reviewer stands out for what it demands of each finding, and several public sources set it out. Cloudflare's audit guide only accepts a security finding if it names who crosses which trust boundary and what concrete result follows. It also gives severity only to what is confirmed<Cite n={14} />.

Anthropic's security reviewer only reports what it considers exploitable with more than 80% confidence. It also explicitly discards categories that tend to be noise<Cite n={15} />. ECC requires citing the exact line, reading the functions that call the reviewed code and accepting that a review with no findings is valid<Cite n={16} />. Google's review guide asks reviewers not to accept changes that degrade the code health of the system<Cite n={17} />.

Each subagent spends tokens on its own model, and the `model` field decides which. If neither the call nor the definition sets it, Claude Code uses the model in the `CLAUDE_CODE_SUBAGENT_MODEL` variable and, without it, the main conversation's model<Cite n={13} repeat />. So if the conversation uses the top model, subagents with no model of their own use it too. A reviewer that searches files does not need the same model as one that reasons about authorisation, so each definition sets its own.

If several subagents edit the same directory at once, one can overwrite another's changes. A git **worktree** prevents it: it is another directory of the same repository, with its own branch. Each subagent works in its own, and the main agent merges the branches one at a time. In Claude Code it is switched on with `isolation: worktree` in the subagent's definition. By default, the worktree starts from the remote's default branch, not the current one<Cite n={18} />.

The six work agents split the same way, each with its own model tier:

1. `explorer` locates and explains code, with a small model.
2. `architect` designs the change and splits it into pieces, with the top model.
3. `implementer` builds one piece in its own worktree, with a mid model.
4. `build-fixer` gets the build, the types and the linter back to green with the smallest change, with a mid model.
5. `doc-writer` brings the documentation up to date, with a small model.
6. `cleaner` clears dead code and duplication on request, with a mid model.

Only the main agent launches them, and it merges their branches one at a time.

A *workflow* is a script that launches dozens of subagents in stages. Claude Code warns when a workflow schedules more than 25 agents. It also accepts a size guideline that aims for fewer than 5, 10 or 50 agents<Cite n={19} />.

**How to do it.**

1. Create `.claude/agents/quality-reviewer.md` with the example.
2. Run it by naming it: `@agent-quality-reviewer review the current diff`<Cite n={13} repeat />.

The prompt in section 14 creates the four reviewers, the six work agents and the `review-change` skill that runs the review.

**How to check it.** Introduce two quality bugs on purpose, a utility that already exists reimplemented and an unused import, and run the reviewer. If it does not flag them, its instructions are not enough.

## 11. What plugins are and what installing one costs

A **plugin** is an installable package that bundles skills, agents, *hooks* and MCP servers<Cite n={20} />. **MCP**, short for Model Context Protocol, is an open protocol for connecting a model to external data sources and tools<Cite n={5} repeat />. An MCP server adds new tools to the agent, for example for Slack, Jira, a database or a browser.

Plugins are distributed through catalogues called *marketplaces*. Anthropic's official one, `claude-plugins-official`, is registered the first time you open an interactive session, so installing from it takes a single command<Cite n={20} repeat />:

```shell
/plugin install commit-commands@claude-plugins-official
```

`commit-commands` is the plugin's name, and it adds commands for committing, pushing and opening pull requests. What follows `@` is the catalogue it comes from. A third-party catalogue is registered first with `/plugin marketplace add <owner>/<repo>`, which installs nothing<Cite n={20} repeat />. `/plugin` with no arguments opens the panel of catalogues, installed plugins and load errors, and `/mcp` manages connections to MCP servers<Cite n={21} />.

Before installing, each plugin's details show two things. **Context cost** is what it adds to every message, and what its skills and agents add once loaded. **Will install** lists the commands, agents, skills, *hooks* and servers it brings<Cite n={20} repeat />. The first takes up context in every session, including the ones that never use the plugin.

Code intelligence plugins connect a language server, the component that gives an editor features such as go-to-definition. With one installed, the agent sees the type errors its own edits introduce without waiting for a build. The plugin does not include the server, which is installed separately<Cite n={22} />.

<Callout kind="riesgo" title="A plugin runs code with the permissions of whoever installs it">
	According to the documentation, an installed plugin can execute arbitrary code on the machine with your account's permissions. Anthropic adds that it does not control what servers, files or other software a plugin includes, and cannot verify that it works as intended<Cite n={23} />. Before installing a third-party plugin, open its repository and read what it brings.
</Callout>

**How to check it.** Run `/context` before and after installing. If a plugin adds context every turn and you never use it, uninstall it.

## 12. Which permissions to give the agent

An agent runs commands and reads files. Before the first long session there are two things to decide: when it stops to ask, and which files it can read.

The first is set by the **permission mode**, which you change with `Shift+Tab` and see in the status bar. These are the main modes and what each one does without asking<Cite n={8} repeat />:

| Mode | What it does without asking |
|---|---|
| `default` | Reads only. Claude Code calls it Manual, and the status bar shows it as `manual mode on`. |
| `acceptEdits` | Reads, edits files and runs basic file commands such as `mkdir` or `mv`. |
| `plan` | Reads and explores, but does not edit the code. |
| `auto` | Everything, with background safety checks. |
| `bypassPermissions` | Everything, with no checks at all. |

From version 2.1.283, terminal and VS Code sessions start in `auto`<Cite n={8} repeat />. The documentation restricts `bypassPermissions` to isolated environments, such as containers or virtual machines, where the agent cannot cause damage<Cite n={24} />.

The second matters because the agent sends the content of the files it reads to the provider's server. A `.env` with credentials goes out just like the code. To exclude it, declare the rule in `.claude/settings.json`<Cite n={25} />:

```json
{
	"permissions": {
		"deny": ["Read(./.env)", "Read(./.env.*)"]
	}
}
```

`deny` is the list of actions Claude Code always refuses. `Read(./.env)` is the read tool on that exact file, and `Read(./.env.*)` covers `.env.local`, `.env.production` and the rest.

Being in `.gitignore` does not protect the file. In the measurement, without the rule, the read tool returned the file with no error. With the rule, it returns this block:

```text
File is in a directory that is denied by your permission settings.
```

The rule also covers shell commands that name the file, such as `cat .env` or `head .env`. It does not cover a script that opens the file itself, such as a Node or Python program<Cite n={24} repeat />.

Cursor works differently. By default it ignores what `.gitignore` lists plus a built-in list that includes `.env*`, and anything else is excluded in `.cursorignore`. Its documentation warns that the agent's terminal and external tools cannot block access to what that file covers<Cite n={26} />.

In both products, the exclusion is declared in configuration, not in the instructions file. Permission rules are enforced by the harness, not the model<Cite n={24} repeat />. So a line in `AGENTS.md` saying "do not read `.env`" does not change what Claude Code allows.

One cost decision remains: which model the session uses. Change it with `/model`. The documentation recommends starting with Sonnet, which handles most coding tasks well and costs less than Opus<Cite n={6} repeat />.

**How to check it.** Ask the agent for the contents of `.env`. With the rule in place, the read tool returns the block instead of the file. The model replying that it will not do it checks nothing, because the rule did not produce that reply.

## 13. How to review what the agent did

The agent edits files directly, so what is left when it finishes is a *diff*. A *diff* is the list of lines that changed between the previous state of the repository and the current one. The diff is only useful if the starting point was clean. That is why `git status --porcelain` has to print nothing before the request.

The usual command to see which files changed does not show the new ones:

```bash
git diff --stat
```

```text
 package.json  |  4 +++-
 src/orders.js | 10 ++++++++++
 2 files changed, 13 insertions(+), 1 deletion(-)
```

The session had also created `src/util/date.js`. `git diff` with no arguments compares the files in the working directory with the index, the area where the next commit's changes are staged<Cite n={27} />. A new file is not in the index yet, so it does not show up. To get the complete list, add everything to the index before looking:

```bash
git add -A && git diff --cached --stat
```

```text
 package.json     |  4 +++-
 src/orders.js    | 10 ++++++++++
 src/util/date.js |  3 +++
 3 files changed, 16 insertions(+), 1 deletion(-)
```

`git add -A` stages everything modified, deleted and new. `--cached` compares the index with the last commit, and `--stat` summarises the changes per file. The missing file imports a new dependency declared in `package.json`, and the request asked for none. That dependency enters the lockfile, installs on every deploy and has to be kept up to date.

Read three things first:

1. Files the request did not name.
2. Deleted lines, because an agent rewriting a whole function can drop a check that was needed.
3. Changes to configuration, the `Dockerfile` and continuous integration, which decide what runs outside your machine.

A change that builds does not show that it does what was asked either, because it can pass the linter without meeting the request. The last check is running the program along the path the change touches. Inside the session, `/diff` shows the same, including the agent's edits<Cite n={21} repeat />.

<Callout kind="riesgo" title="Discarding a whole session is two commands, and both delete">
	`git reset --hard` returns everything git already tracks to the last commit, and `git clean -fd` deletes the files that are not in the index yet. What they remove is not in the history, so it cannot be recovered. Before running them, check that your own work is already committed.
</Callout>

**How to check it.** Run `git add -A && git diff --cached --stat` and compare that list with the request. Read in full every file that does not belong before continuing.

## 14. How to set up the whole environment with one prompt

Everything above can be set up by hand, file by file. The agent can also do it with a prompt, in whichever harness receives it. Copy it with the **Copy prompt** button in the **Set up environment** panel and paste it into a session opened at the project root. The agent follows eleven phases:

1. **Surveys the project** without writing anything. It finds out which harness it runs in, which models it offers and which tier each one is in, and the project's language. It also looks for the real test, lint, type and audit commands, and for how the project authenticates and authorises.
2. **Proposes and waits.** It presents the files it will create and the model for each subagent, and stops until you confirm. It also includes the recommended optional tools, each with what it sends off the machine.
3. **Writes `AGENTS.md`** with the checked commands, the conventions, an optional part for domain vocabulary and which skill or agent to use in each situation.
4. **Blocks reading secrets** with its harness's permission rule, and checks it by trying to read `.env`.
5. **Creates four method skills.** `clarify` asks you questions in rounds before building, with its recommended answer to each one. The agent looks up in the code whatever can be found there, and the decisions are yours. `test-first` and `root-cause-debugging` set the failing-test cycle and the search for the root cause. `orchestrate` decides how many subagents to launch, at what model tier, and when to use worktrees and *workflows*.
6. **Creates the four reviewers from section 10.** The security one carries a project context file and nine per-domain checklists, which it loads depending on what the change touches. The quality one also checks whether the change does what was asked, with what is missing and what is extra. The errors and types one looks for silent failures, `catch` blocks that hide errors, misleading fallback values, impossible states and forced conversions.
7. **Creates the six work agents from section 10**, each with its own model tier.
8. **Creates the `review-change` skill**, which runs the security, quality and errors reviewers in parallel, leaves the tests one for last and composes the verdict.
9. **Proposes optional settings**: the default subagent model, the workflow size, the base branch for worktrees and three *hooks*. The hooks format the code, protect sensitive files and block destructive commands such as `git push --force`, `git reset --hard` or `rm -rf`.
10. **Proposes three tools and two skill collections, all optional**, and asks before installing each one: graphify, claude-council, archify, Matt Pocock's skills and gstack.
11. **Checks and closes.** It seeds one flaw per reviewer on a temporary branch, checks that each reviewer catches its own and deletes the branch. Then it asks the architect for the plan of a sample task and repeats the check of the installed tools.

The base setup, phases 1 to 9, takes 15 to 20 minutes on a small project. In the measured run it took 14: 5 to survey the project and propose, 2 waiting for the answer and 7 to create the files.

With the five optional tools and the phase 11 checks, the whole run took 29 minutes. Two things account for the difference. gstack compiles its binaries and downloads its browser, which takes about 5 minutes. The reviewer check takes about 8. It launches the four reviewers on the planted flaws, and the tests reviewer mutates the code to see whether any test catches it.

In that check, the four reviewers caught the four planted flaws, and the security reviewer confirmed the injection by running it. The tests reviewer also showed that a planted test stayed green with the function broken.

On a sample Node.js project, with the five optional tools installed, the prompt left this structure. `.claude/agents` holds the ten subagents: the four reviewers and the six work agents. `.claude/skills` holds sixteen skills: the prompt's nine, graphify's and six of Matt Pocock's. What installs into your home folder (archify, gstack and claude-council) appears at the bottom, collapsed, with its path under `~/.claude`.

## 15. What each piece contributes and where it comes from

Without this setup, the agent starts every session without knowing the project's commands and can read a `.env` without asking. It also reviews its work with the same bias it wrote it with, and its subagents use the session's model (section 10). Each piece of the prompt solves one of those problems:

- **`AGENTS.md`** records the project's facts (the checked commands, the vocabulary and the conventions), so the agent does not have to work them out again in every session.
- **The secrets rule and the *hooks*** turn limits into rules the harness enforces. Reading `.env` and running destructive commands are blocked even when the model tries.
- **The method skills** give a procedure for each kind of task. With them, the agent clarifies before building, sees the test fail before writing code and finds the cause before fixing. It also splits work with the right number of agents and the right models.
- **The reviewers** split the review into four questions, each in its own context and free of the bias of whoever wrote the change.
- **The work agents** take bounded pieces of a large task, each on the model tier it needs.

The ideas come from nine public sources:

1. **Cloudflare's audit guide**<Cite n={14} repeat /> gives the `security-reviewer` its method: evidence in the source, a safe reproduction and the smallest fix. It also gives its severity scale and its nine per-domain checklists.
2. **Anthropic's security reviewer**<Cite n={15} repeat /> contributes the list of categories the `security-reviewer` does not report, such as denial of service, because they are almost always noise.
3. **Trail of Bits' skills**<Cite n={28} /> review only what a change introduces and whom it affects. They also check each suspicion to rule out false positives, and mutate code to measure the tests. Those three ideas are in the reviewers' shared contract and in the `tests-reviewer`.
4. **Anthropic's official `pr-review-toolkit` and `feature-dev` plugins**<Cite n={29} /> bring reviewers for silent failures, type design and test coverage. They also bring agents that explore the code and design before implementing. They are the source of the `errors-and-types-reviewer`, the `tests-reviewer`'s scoring of what the tests do not cover, the `explorer` and the `architect`.
5. **ECC**<Cite n={16} repeat /> has bounded work agents: one fixes the build with the smallest change, another clears dead code and another brings the documentation up to date. They became the `build-fixer`, the `cleaner` and the `doc-writer`.
6. **Google's review guide**<Cite n={17} repeat /> says what to look for in a review and asks for every line to be read. It gives the `quality-reviewer` its question and its list of categories.
7. **Superpowers**<Cite n={30} /> contributes three habits: see the test fail first, find the root cause and stop after three failed fixes, and claim nothing without the command that proves it. It also picks the cheapest model that can do each task, because the number of turns affects cost more than the price per token. It is in `test-first`, `root-cause-debugging`, the end of `AGENTS.md` and the tiers in `orchestrate`.
8. **Matt Pocock's skills**<Cite n={31} /> ask you questions before building and check whether a change does what was asked. They also resolve merge conflicts by each side's intent. They gave `clarify`, the "What was asked" part of the `quality-reviewer` and the merge rule in `orchestrate`.
9. **gstack**<Cite n={32} /> reuses what exists before writing new code and warns before a destructive command. It also treats agreement between two models as a hint, and the decision stays yours. It is in the `implementer`, the destructive-command hook and the way claude-council is used.

From the CC BY-SA sources only ideas are taken; the text is original.

## 16. Which optional tools the prompt proposes

Besides what it creates, the prompt proposes three tools and two skill collections, all optional.

**graphify** turns the repository into a knowledge graph: which function calls which, which module imports which, and which files make up a subsystem. The agent queries it before opening files one by one, for instance to find everything that uses a function before changing its signature.

graphify analyses the code locally with tree-sitter, a syntax parser, with no language model involved. Documentation, PDFs and images, on the other hand, do go to the agent's model. Building the graph from the terminal, with `graphify update .`, sends nothing off the machine<Cite n={33} />.

**claude-council** is a third-party plugin for Claude Code that asks the same question to several models. It shows the answers side by side, with a summary of where they agree and disagree. It suits design decisions where a single model's bias could mislead, such as choosing between two data structures.

With API providers, such as OpenAI, Gemini or Grok, the plugin sends those third parties the question and up to five project files it adds by itself. The `--local` mode, using Claude subagents, and the `ollama` mode send nothing off the machine<Cite n={34} />.

**archify** is a skill with a Node.js command-line program. It turns a description or a repository into an interactive diagram, as a single self-contained HTML file. There are five types: architecture, workflow, sequence, data flow and lifecycle.

archify shows how a project's pieces connect, including code the agent wrote, and it validates the diagram before handing it over. It sends no project data. Roughly every 72 hours it runs an optional check for new versions, in which the server sees only the IP address and the time<Cite n={35} />.

**Matt Pocock**'s skills, `mattpocock-skills`<Cite n={31} repeat />, ask you questions before building, apply test-first and debug. They also review a change against the repository's own standards and against what the task asked for. Its `tdd`, `diagnosing-bugs`, `code-review` and `grill-me` skills overlap with the prompt's own. When you install them, the prompt proposes keeping one from each pair.

They are Markdown instructions and send nothing by themselves. They also bring what the prompt lacks. `to-spec` and `to-tickets` turn a conversation into a specification or into tasks. `improve-codebase-architecture` improves the architecture of existing code, and `handoff` passes the work to another session.

**gstack**<Cite n={32} repeat /> is a complete development process with roughly forty skills for planning, reviewing, testing in a browser, publishing and running retrospectives. It installs into your user account, outside the project, and needs Bun. Its installer compiles its own browser and registers a *hook* in the global configuration, `~/.claude/settings.json`.

In team mode, gstack adds another *hook* that pulls and reinstalls the latest version whenever a session opens, at most once an hour. That is why the prompt proposes it without team mode and with telemetry off. It also skips importing the browser's cookies, which would hand the agent your signed-in sessions.

**How to do it.** Phase 10 of the prompt proposes the three tools and the two collections one at a time, and only installs each one if you confirm.

## 17. How to work with the environment: a new feature from start to finish

With the environment set up, the agent already knows the project's commands and conventions, and has a procedure for each step. This example follows a new feature in the sample project, from the request to the commit.

**The request.** Type `/plan` followed by what you want and the requirements you already know. In plan mode the agent reads, searches and runs exploration commands, but edits nothing until you approve the plan<Cite n={8} repeat />:

```text
/plan Add discounts to orders. resumen() has to show the final amount,
no total may drop below zero, and the change comes with its tests.
```

**What the environment does with that request:**

1. **It starts from `AGENTS.md`.** The agent already knows that tests run with `npm test`, that amounts are integer cents and that only `formatearPrecio` turns them into text. It does not have to work that out from the code.
2. **It clarifies before planning.** The request leaves decisions open, so the agent uses `clarify`. The agent looks up what it can find in the code and asks you the rest in rounds, with a recommendation for each question. In the section 14 run, faced with a similar request, it asked (translated from Spanish):

   ```text
   1. What kind of discount? a) percentage, b) fixed amount in cents, c) both.
      I recommend b: it is an integer from the start and needs no rounding decision.
   3. What happens if the discount is larger than the total? a) throw an error, b) the net stays at 0.
      I recommend a, consistent with the TypeError that formatearPrecio throws.
   ```

3. **It designs and splits.** With the decisions made, `orchestrate` decides whether the task is worth splitting. If it is, the `architect`, on the top model, splits it into pieces that share no files. Each piece carries its test, its check command and its model tier. Before proposing new code it looks for what already exists, here `formatearPrecio`.
4. **You approve the plan.** The plan appears as text: you can approve it, ask for more planning or edit it with `Ctrl+G`<Cite n={8} repeat />. You correct a wrong approach in that text, with no files to revert.
5. **It implements test first.** Each piece follows `test-first`. First comes the test for the behaviour, for instance that a discount larger than the total throws an error, and the agent checks that it fails; then the minimal code. If there are independent pieces, each `implementer` works in its own worktree. The main agent merges them one at a time and runs the suite after each merge.
6. **The limits stay on.** If the agent tries to read `.env`, edit `package-lock.json` or run `git reset --hard`, the permission rule and the *hooks* block it. It does not depend on the model remembering.
7. **It reviews before committing.** `AGENTS.md` asks for `review-change` before every commit, and you can also run it with `/review-change`. The quality reviewer compares the change with the approved plan, and the errors and types reviewer looks, for example, for a negative discount nobody validates. The tests reviewer mutates the discount logic to see whether any test catches it.
8. **It commits.** If the verdict is clean or only has warnings, the agent commits the change in the project's commit format. If something blocks, it fixes it and reviews again.

The optional tools fit into the same steps. The `explorer` queries graphify before opening files, and archify draws the flow if you ask for it. claude-council helps with an uncertain decision, such as percentage versus fixed amount.

**What the project gains.** Each step prevents a specific kind of error:

- A decision nobody made, such as the kind of discount or what happens with negatives, is asked about before any code is written, instead of turning up in review.
- A forgotten convention, such as formatting an amount outside `formatearPrecio`, is written down in `AGENTS.md`, and the quality reviewer checks it.
- A test that passes by construction protects nothing, so `test-first` requires seeing it fail and the tests reviewer mutates the code to check.
- A security flaw is reviewed by another agent, in its own context, which confirms it by running it. It does not depend on whoever wrote it noticing it.
- A secret or a destructive command does not depend on anyone's attention, because the harness blocks it.

Section 14 shows the result of that review on planted flaws.

**How to do it.**

1. Type `/plan` followed by the request, or press `Shift+Tab` until plan mode and type the request.
2. Answer the `clarify` questions and approve the plan.
3. During implementation, check `/context` to see how much of the window the conversation takes, and use `/rewind` to undo a step that went wrong.
4. Before committing, run `/review-change` if the agent has not already.

## Where to go next

Start with the check: a command that says whether a task is done (section 4). Then add the instructions file, the skills and the reviewers as a task repeats. You can also generate them in one go with the prompt in section 14 and adjust them afterwards.
