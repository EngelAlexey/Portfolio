The code a language model generates, from a chat or from an agent, compiles, passes the tests and does what its task description asked. That description rarely includes the security requirements, such as who may see or change each piece of data. So the result does not meet them either.

Veracode tested more than a hundred models on coding tasks in four languages. Of the generated code samples, 45% failed the security tests. Newer and larger models did no better than small ones<Cite n={1} />. The result therefore depends on the method used to generate the code, not on the model that writes it.

The seven failures that follow are the ones that repeat most in generated code. Each one belongs to a layer of [How to secure a web application](/en/blog/how-to-secure-a-web-application). That guide explains how to apply each layer and how to check it. Here you see the same failure in the code, with its fix and the command that checks it.

| Section | Layer in the guide |
|---|---|
| 1 and 2 | Permissions |
| 3 and 5 | Input and output |
| 4 | Secrets |
| 6 | Dependencies |
| 7 | Errors and logs |

Every example was rebuilt for the article and none of them comes from a production system.

## 1. How to check the permission on the server

The component hides the button by role, and the endpoint deletes the invoice without checking anything.

```tsx
{user.role === 'admin' && <button onClick={remove}>Delete invoice</button>}
```

```ts
// app/api/invoices/[id]/route.ts
export async function DELETE(req: Request, { params }: Ctx) {
  await db.invoice.delete({ where: { id: params.id } });
  return Response.json({ ok: true });
}
```

Hiding the button is a rendering decision, not a permission. The endpoint still accepts the request from anyone who knows the address, and that address sits in code the browser has already downloaded. The OWASP API Security Top 10 lists this failure as API5:2023, Broken Function Level Authorization. It means that a server function does not check the permission of whoever calls it. OWASP also notes that authorisation is managed in configuration or in code<Cite n={2} />.

Repeat the check on the server, the only place the user cannot modify:

```ts
export async function DELETE(req: Request, { params }: Ctx) {
  const session = await auth();
  if (session?.user.role !== 'admin') return new Response(null, { status: 403 });

  await db.invoice.delete({ where: { id: params.id } });
  return Response.json({ ok: true });
}
```

On a multi-tenant platform, adopt a stricter version of this rule from day one. All authorisation is decided in the application code. The application's database account grants access to the process, never to the person who made the request.

**How to check it.** Skip the interface and send the request with the session of a user who is not an administrator:

```bash
curl -i -X DELETE http://localhost:3000/api/invoices/42 \
  -H "Cookie: session=$REGULAR_USER_SESSION"
```

Without the fix, the response is `200 OK` and the invoice is gone. With the fix, the response is `403` and the invoice is still there.

## 2. How to check who owns a record loaded by id

The query looks the invoice up by the identifier in the URL and by nothing else.

```ts
export async function GET(req: Request, { params }: Ctx) {
  const invoice = await db.invoice.findUnique({ where: { id: params.id } });
  return Response.json(invoice);
}
```

This endpoint does require a session, so it looks correct. Even so, any user with a session can read another company's invoices by changing the number in the address. The same OWASP list puts this failure in first place, as API1:2023. It describes it as manipulating the identifier sent inside the request<Cite n={3} />.

To fix this case and every case like it, include the owner in the query condition. A check that runs afterwards can be forgotten in the next endpoint. A condition inside the `where` applies every time the query runs.

```ts
const session = await auth();
const invoice = await db.invoice.findFirst({
  where: { id: params.id, companyId: session.user.companyId }
});

if (!invoice) return new Response(null, { status: 404 });
return Response.json(invoice);
```

The fix answers `404` and not `403` on purpose. A `403` confirms that the invoice exists, and that confirmation is already information about another company.

**How to check it.** Use two sessions. Sign in as company A, request an id that belongs to company B and check that the response is `404`.

## 3. How to build a query without concatenating text

The filter comes from a search form and enters the SQL statement as text.

```ts
const rows = await db.$queryRawUnsafe(
  `SELECT * FROM invoices WHERE client = '${req.nextUrl.searchParams.get('client')}'`
);
```

The value lands inside the quotes and can close them. With `x' OR '1'='1`, the condition is always true and the query returns the whole table. OWASP recommends not passing the value to the SQL interpreter as text, and using a parameterised interface or an ORM instead<Cite n={4} />.

The fixed version uses `$queryRaw` with a tagged template, which is a string with `${}` passed to a function. The function receives the value separately and sends it as a parameter, not as part of the statement:

```ts
const client = req.nextUrl.searchParams.get('client') ?? '';
const rows = await db.$queryRaw`SELECT * FROM invoices WHERE client = ${client}`;
```

One case remains that a parameter cannot cover: the name of the column used for sorting. A parameter replaces a value, not a column name, so the only defence there is a closed list:

```ts
const COLUMNS = { date: 'issued_at', amount: 'total' } as const;
const column = COLUMNS[sort as keyof typeof COLUMNS] ?? 'issued_at';
```

If a model writes the query while the application runs, the check has to happen on the parsed statement. A regular expression over the text fails, because a comment, a space or an alias is enough to hide the query from it. Parse the statement to get its syntax tree, add the security filters there and run only the statement that results.

**How to check it.** Send the value with the quote:

```bash
curl "http://localhost:3000/api/invoices?client=x%27%20OR%20%271%27%3D%271"
```

Without the fix, the response contains every invoice. With the fix, it contains an empty list, which is the right answer for a client that does not exist.

## 4. How to keep a secret out of the browser

The variable has to be available inside the component, so the model gives it the prefix that makes it public.

```ts
const stripe = new Stripe(process.env.NEXT_PUBLIC_STRIPE_SECRET_KEY!);
```

According to the Next.js documentation, the value of a variable with the `NEXT_PUBLIC_` prefix is inlined into the bundle at build time. The bundle is the JavaScript the browser downloads, and in it every reference to the variable is replaced by its value<Cite n={5} />. The same happens with `VITE_` and with `PUBLIC_` in Astro.

The fix is to keep the key on the server. The component calls a route of its own, and that route calls Stripe with the key:

```ts
// app/api/payments/route.ts
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);

export async function POST(req: Request) {
  const intent = await stripe.paymentIntents.create({ amount: 1500, currency: 'usd' });
  return Response.json({ clientSecret: intent.client_secret });
}
```

A protection that depends on remembering the prefix fails the day someone forgets it. [The secrets layer in the guide](/en/blog/how-to-secure-a-web-application#10-how-to-keep-secrets-out-of-the-code-and-the-browser) explains how to detect them before the commit and where to store them.

**How to check it.** Search the build output, not the source code. Next.js puts the bundle in `.next/static`. Search for the start of the key's value, `sk_live`, not for the variable name, because the build has already replaced one with the other:

```bash
pnpm build && grep -r "sk_live" .next/static | head
```

The output has to be empty.

<Callout kind="riesgo" title="A key that reached the browser is already exposed">
Removing the prefix does not make it secret again. The value has been published and may sit in someone's cache, in an earlier deployment or in a repository. Generate a new key at the provider, revoke the exposed one and then change the code.
</Callout>

## 5. How to validate input in the endpoint

The form limits the field, and the endpoint assumes that the value arrived limited.

```tsx
<input type="number" name="quantity" min={1} max={5} required />
```

```ts
export async function POST(req: Request) {
  const { quantity } = await req.json();
  await db.order.create({ data: { quantity, total: quantity * PRICE } });
}
```

The `min`, `max` and `required` attributes help the person filling in the form, but a request sent outside the form never passes through them. With a negative quantity, the stored total comes out negative. The CWE catalogue lists it as CWE-602: enforcing on the client a protection that belongs to the server<Cite n={6} />.

Validate at every trust boundary, the point where data passes from something the user controls to something they do not. An endpoint is one of those boundaries, and so are a message queue and a webhook. The fix validates the body with a Zod schema before creating the order:

```ts
const Body = z.object({ quantity: z.number().int().min(1).max(5) });

export async function POST(req: Request) {
  const parsed = Body.safeParse(await req.json());
  if (!parsed.success) return new Response(null, { status: 400 });

  const { quantity } = parsed.data;
  await db.order.create({ data: { quantity, total: quantity * PRICE } });
}
```

`safeParse` returns the result of the validation instead of throwing an exception, and the endpoint answers `400` when it fails.

**How to check it.** Send a value the form does not let you type:

```bash
curl -i -X POST http://localhost:3000/api/orders \
  -H "Content-Type: application/json" \
  -d '{"quantity": -3}'
```

Without the fix, the response is `200` and the order is created. With the fix, the response is `400` and nothing is created.

## 6. How to check that a package exists before installing it

This failure is not in the code but in `package.json`. The model suggests a package with a plausible name that was never published to the npm registry, where packages are installed from. The name in the example was invented for the article and did not exist in the registry on 7 September 2026.

```json
"dependencies": {
  "react-input-sanitizer-pro": "^2.1.0"
}
```

A **hallucinated package** is a package name the model invents. A study published at USENIX Security 2025 generated 576,000 code samples with 16 models and found 205,474 distinct hallucinated names. At least 5.2% of the packages named by commercial models did not exist, and 21.7% of those named by open-source models<Cite n={7} />.

The invented name is predictable, so anyone can publish it to the registry with their own code. From then on, that code is installed in every project that follows the suggestion. A package can also declare install scripts, which are commands the package manager runs when it installs the package. If the package manager runs them, the publisher's code runs before anyone imports the package.

Whether the package manager runs them depends on the version: yarn 1 runs them with no exceptions, and npm ran them up to version 11. In npm 12 and pnpm 10 they are blocked, except for the packages that appear in a list declared separately. The article [npm vs pnpm 11: install script security and allowBuilds](/en/blog/npm-vs-pnpm-install-security) measures four versions of the two package managers.

**How to check it.** Before installing, query the registry:

```bash
npm view react-input-sanitizer-pro time.created maintainers repository.url
```

Three answers argue against installing:

1. An `E404` means the package does not exist.
2. A creation date a few days old means someone may have registered it to take advantage of the invented name.
3. A missing repository, or one that does not match the name, means there is nothing to audit.

<Callout kind="nota" title="Pin the version and commit the lockfile">
The lockfile, `package-lock.json` in npm, records the exact version of every dependency. A range like `^2.1.0` accepts versions that do not exist yet when it is written. `npm ci` installs what the lockfile says and fails when it does not match `package.json`, instead of updating it<Cite n={8} />. With that file in the repository, a new version does not get in without someone reviewing it.
</Callout>

## 7. How to return an error without exposing internal detail

The handler returns the whole error to the client, which is convenient during development.

```ts
catch (error) {
  return Response.json({ error: error.message, stack: error.stack }, { status: 500 });
}
```

The message of a database error names the table, the column and the constraint that failed. The stack trace, the list of calls that led to the error, names the server paths and the dependency versions. This is CWE-209: an error message that reveals information about the environment or its data<Cite n={9} />. That information reduces the work of anyone looking for a vulnerability.

Keep the detail in the server log, which only the team reads, and return an identifier to find it later:

```ts
catch (error) {
  const id = crypto.randomUUID();
  console.error(id, error);
  return Response.json({ error: 'internal_error', id }, { status: 500 });
}
```

The log is not a private place either. It is exported, sent to a provider and read by people who do not need to see all of it. Scrub personal data before writing it to the log, not when someone asks for access. [The errors layer in the guide](/en/blog/how-to-secure-a-web-application#12-how-to-answer-errors-without-leaking-data) shows the same fix measured in Express.

**How to check it.** Cause the failure: stop the database, send the request and read the response body. No table name and no server path can appear in it.

## 8. How to review generated code with a prompt

You can review the seven sections by hand. A coding agent can also do it with a prompt, on recent changes or on the whole repository. Copy it with the **Copy prompt** button in the **Review the code** panel and paste it into a session opened at the project root. The agent follows seven phases:

1. **It asks what to review:** a range of commits, a branch or the whole repository if it is small.
2. **It reviews the seven sections** with their checks, and confirms each failure by running the check when it can.
3. **It proposes and waits.** It presents the failures, from most to least serious, and the fix for each one, and stops until you confirm.
4. **It fixes** each failure with the smallest change that closes it.
5. **It adds a test** per failure and checks that it fails before the fix.
6. **It repeats the checks** and pastes the outputs from before and after.
7. **It delivers a report** with what changed, what it could not check and the guide layer each failure belongs to.

The run was measured with Claude Code 2.1.283 on an Express invoicing API with the seven failures. It took 6 minutes, not counting the wait for confirmation: 3 up to the proposal and 3 to fix and check.

The agent found the seven failures, confirmed each one with a check and assigned it to its layer. It also found an eighth that fails open: with the token `__proto__`, the session lookup returned the object's prototype and the request went through. The nine tests it added failed before the fixes, and all pass afterwards. It also warned that the exposed key was still in the git history.

<Callout kind="riesgo" title="Read the prompt before pasting it">
	This prompt asks the agent to run the project's commands and change the code. The full text opens with **Show the full prompt**, under the button, and it is exactly what gets copied. Phase 3 makes the agent stop before writing; if it carries on without asking, interrupt it.
</Callout>

**How to check it.** `git status` and `git diff` show only the confirmed fixes and the new test files, and the tests pass.

## What to fix first

The seven failures are not equally urgent. Sections 1, 2 and 4 can be exploited from outside with no other failure and without crafting any value, so they go first. Sections 3 and 5 need someone to send a value crafted on purpose, such as a quote or a negative quantity. That is cheap, but deliberate. Section 6 is checked when a dependency is installed, and section 7 is fixed once in the shared error handler.

**Failing closed** means denying the request when a check cannot decide. That rule applies to all seven cases. For example, the request is refused if the session does not resolve, if validation throws an exception or if the permission is missing. Generated code tends to do the opposite. A `?? 0`, an empty `catch` or an `if (!user) return next()` let the request carry on as normal, and the failure goes unnoticed.

Unescaped HTML, [an open CORS configuration](/en/blog/what-is-cors) and a missing rate limit are left out of the list. They are common failures, but they do not repeat as much in generated code. [How to secure a web application](/en/blog/how-to-secure-a-web-application) covers them in its input and output, other origins, and passwords and attempts layers. The last one includes the login attempt limit.
