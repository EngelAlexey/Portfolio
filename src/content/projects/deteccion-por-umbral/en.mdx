## Context

An individual final project for IT Security I, the same course as the [spyware analysis](/en/projects/analisis-spyware). The brief asked for a tool that would detect and contain mass encryption on its own, plus a test bench to exercise it on.

The scenario it models is an organisation attacked by a program nobody has seen before. In that case there is no signature to recognise, and containment has to be decided from what the operating system can observe while it happens.

The exercise runs on an ephemeral AWS instance brought up for it. Nothing that executes there touches a system in use.

## Problem

Signature-based antivirus only recognises what has been seen before. Against a new binary it does not fire, and the encryption advances while somebody identifies it.

Waiting for a person to notice does not work either: by the time someone opens a file and finds it unreadable, the encryption has already crossed the disk.

The question becomes a different one: what does the operating system observe when something encrypts files en masse, and how much of that can be measured without identifying the program.

## Technical decisions

Three independent signals, none conclusive on its own.

Filesystem events say there is activity. The entropy of what is being written says the content has stopped looking like a document. Sampling `write_bytes` per process, every 500 ms, says who is doing the writing.

A separate component combines the three into a score, and only that score decides to contain. The sensors contain nothing, so thresholds are tuned without touching them.

## Architecture

A filesystem watcher drops events into a locked buffer. A sampling thread keeps the most recent picture of per-process writes. The main thread reads the score every second and decides whether to act.

Containment kills the process tree and moves the binary to a quarantine directory with no execute permission.

The test bench's infrastructure is described in Terraform, so the lab is created and destroyed with one command and every run starts from the same machine. Terraform state and the variables file stay out of version control, because a state file holds sensitive values in the clear.

## Result

The detector contains mass encryption without having seen the binary before and without anyone intervening. It reacts to what the process does, which was the point of the exercise.

The test bench is reproduced with one command, so every threshold adjustment was measured from the same starting machine and the results compare across runs.

## What I learned

The threshold was the hard part. A legitimate backup produces a pattern very close to mass encryption: many files written fast, with high-entropy content.

With the three signals available I found no value that separated the two cases. The delivered version prioritises not missing a real case and accepts false positives, and the threshold is documented with that justification. When two cases are indistinguishable from the data you have, the decision stops being technical and becomes which of the two errors costs more.
